# การสกัดข้อความและคิวงาน (Search indexing)

เอกสารนี้อธิบายกลไกที่อยู่เบื้องหลัง [CONTENT_SEARCH.md](CONTENT_SEARCH.md)

## ดัชนีเป็นข้อมูลที่สร้างใหม่ได้

`ResourceSearchIndex` ไม่ใช่ข้อมูลต้นฉบับ มันคือผลลัพธ์ที่คำนวณได้จากไฟล์จริงบนดิสก์

**ระบบต้องทำงานได้ครบทุกอย่างแม้ตารางนี้จะว่างเปล่า** - ค้นจากชื่อไฟล์ แท็ก และหมายเหตุยังได้เหมือนเดิม
อัปโหลด ดาวน์โหลด แชร์ และกู้คืน ไม่ขึ้นกับดัชนีเลย เพียงแต่ค้นจากเนื้อในไม่ได้จนกว่าจะทำดัชนีใหม่

นี่คือเหตุผลที่ความล้มเหลวของการสกัดข้อความไม่เคยทำให้ไฟล์ใช้งานไม่ได้

## ตาราง

หนึ่งแถวต่อหนึ่ง **เวอร์ชัน** ของไฟล์ โดยมี `resourceVersionId` เป็น unique

นี่คือกุญแจของความเป็น idempotent - สั่งทำดัชนีซ้ำกี่ครั้งก็ยังเป็นแถวเดิม ไม่ใช่การสะสมงาน

| คอลัมน์ | ความหมาย |
|---|---|
| `status` | `PENDING` `PROCESSING` `READY` `NO_TEXT` `UNSUPPORTED` `FAILED` |
| `extractedText` | ข้อความตามที่สกัดได้จริง ใช้ตัดตัวอย่างมาแสดง |
| `normalizedText` | ข้อความที่ปรับรูปแบบแล้ว ใช้เป็นเป้าของการค้นหา |
| `truncated` | ข้อความยาวเกินเพดานจึงถูกตัด |
| `extractorVersion` | รุ่นของตัวสกัด ใช้ตัดสินว่าควรทำใหม่เมื่อกติกาเปลี่ยน |
| `errorCode` | รหัสสั้น ๆ ที่ปลอดภัย ไม่มีเส้นทางจริงและไม่มีเนื้อหาเอกสาร |
| `attempts` · `processingStartedAt` | ใช้จำกัดการลองใหม่ และกู้คืนงานที่ค้างหลังเซิร์ฟเวอร์ล่ม |

`ON DELETE CASCADE` ทั้งจาก `Resource` และ `ResourceVersion` - การลบถาวรจึงไม่ทิ้งข้อความที่สกัดไว้ค้างอยู่โดยไม่มีเจ้าของ

## ไม่มีสถานะที่กำกวม

ทุกกรณีมีสถานะของตัวเอง ไม่มีการใช้ `null` แทน "ไม่รู้"

- `NO_TEXT` และ `UNSUPPORTED` **ไม่ใช่ความล้มเหลว** - เป็นข้อเท็จจริงเกี่ยวกับไฟล์ และ `errorCode` เป็น null
- `FAILED` คือพยายามแล้วไม่สำเร็จจริง ๆ เช่นไฟล์เสียหายหรือมีรหัสผ่าน

การแยกสองอย่างนี้ทำให้ผู้ดูแลตอบได้ว่า "ไฟล์ไหนควรทำ OCR ในอนาคต" กับ "ไฟล์ไหนมีปัญหาจริง"

## คิวงาน

คิวอยู่ใน**ฐานข้อมูล** ไม่ใช่ในหน่วยความจำ งานที่รอไว้จึงอยู่รอดข้ามการรีสตาร์ท
และ **ไม่ต้องเพิ่ม Redis เข้ามาในระบบเพียงเพื่อเรื่องนี้**

```
อัปโหลดเสร็จ → เขียนแถวเวอร์ชัน → เข้าคิว (รอ) → ตอบผู้ใช้
                                        ↓
                          ตัวทำงานหยิบไปทำในเบื้องหลัง
```

**รอเฉพาะการ "เข้าคิว"** ซึ่งเป็นการเขียนแถวเดียว ไม่ได้รอให้สกัดเสร็จ
ถ้าไม่รอตรงนี้ งานอาจหายไปเมื่อกระบวนการจบก่อนที่คิวจะถูกเขียนลงฐานข้อมูล
และไฟล์ที่ไม่เคยเข้าคิวจะไม่มีวันถูกทำดัชนีจนกว่าจะมีคนสั่งใหม่

การอัปโหลดจึงเร็วเท่าเดิม และไฟล์ใช้งานได้ทันทีแม้การสกัดจะยังไม่เริ่ม

### การจองงาน

ใช้ `updateMany` พร้อมเงื่อนไขสถานะเดิม ซึ่งเป็นการเปรียบเทียบและเขียนในคำสั่งเดียว
ผู้ทำงานสองคนจึงหยิบงานชิ้นเดียวกันไปทำพร้อมกันไม่ได้ แม้จะมีหลายกระบวนการ

### ลำดับและขีดจำกัด

- เก่าที่สุดก่อน งานที่ค้างมานานไม่ถูกแซงตลอดกาล
- ทำพร้อมกันได้ตาม `S2_NAS_EXTRACT_CONCURRENCY` (ค่าเริ่มต้น 2)
- ตั้งใจให้ต่ำ **การที่ระบบยังรับอัปโหลดได้สำคัญกว่าความเร็วของการค้นหา**
- ทำทีละชุดแล้วคืนเวลาให้คำขอของผู้ใช้ ไม่กวาดจนหมดในรอบเดียว

### การลองใหม่

ความล้มเหลวชั่วคราวกลับเข้าคิวได้สูงสุด 3 ครั้ง
ความล้มเหลว**ถาวร**หยุดทันที - PDF ที่ใส่รหัสผ่านไว้จะไม่เปิดได้เองในรอบหน้า

รหัสที่ถือว่าถาวร: `PDF_INVALID` `PDF_ENCRYPTED` `PDF_TOO_LARGE` `ZIP_*` `FILE_TOO_LARGE_TO_INDEX`

## การกู้คืนหลังเซิร์ฟเวอร์ล่ม

ตอนเริ่มระบบ (ไม่บล็อกการเริ่ม):

1. งานที่ค้างในสถานะ `PROCESSING` เกิน 15 นาที = ล่มกลางคัน → กลับเข้าคิว
2. ไฟล์ที่มีเวอร์ชันปัจจุบันแต่ยังไม่มีแถวดัชนี → สร้างแถวรอไว้ (ครั้งละไม่เกิน 500 แถว)

ข้อ 2 คือการเติมย้อนหลังของไฟล์ที่มีอยู่ก่อน F12 - เกิดขึ้นเองโดยไม่ต้องสั่ง

## ขีดจำกัดด้านทรัพยากร

| ตัวแปร | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `S2_NAS_EXTRACT_MAX_FILE_BYTES` | 64 MB | ไฟล์ใหญ่กว่านี้ไม่ถูกสกัด (ยังอัปโหลด/ดาวน์โหลดได้ตามปกติ) |
| `S2_NAS_EXTRACT_MAX_TEXT_CHARS` | 400,000 | ข้อความยาวเกินนี้ถูกตัด และ `truncated = true` |
| `S2_NAS_EXTRACT_MAX_SECONDS` | 60 | เวลาสูงสุดต่อไฟล์ ไฟล์ที่ทำให้ตัวสกัดค้างต้องไม่หยุดคิวทั้งคิว |
| `S2_NAS_EXTRACT_CONCURRENCY` | 2 | จำนวนงานพร้อมกัน |
| `S2_NAS_EXTRACT_POLL_SECONDS` | 15 | ระยะห่างของการตรวจคิว |
| `S2_NAS_EXTRACT_ENABLED` | 1 | `0` = ปิดการสกัดทั้งหมด ระบบยังทำงานครบ |

**การตัดข้อความถูกบอกตามจริงเสมอ** ไม่มีการทำเหมือนว่าทำดัชนีทั้งฉบับแล้วเงียบ ๆ

## ความปลอดภัยของตัวสกัด

ไฟล์ที่ผู้ใช้อัปโหลดคือข้อมูลที่ไม่น่าไว้ใจ ทุกตัวสกัดปฏิบัติกับมันแบบนั้น

**ไม่ทำโดยเด็ดขาด:** เปิดโปรแกรม Office · รันมาโคร · ประเมินสูตร · ตามลิงก์ภายนอก · รันสคริปต์ที่ฝังอยู่ · เรียกโปรแกรมภายนอก

ไฟล์ถูกอ่านผ่าน `resolveStorageKey` ซึ่งบังคับให้อยู่ในรากของพื้นที่จัดเก็บเสมอ
**ไม่มีเส้นทางจริงบนดิสก์หลุดออกไปที่ใด** ทั้งใน DTO และใน log

### OOXML (DOCX / XLSX / PPTX)

ไฟล์เหล่านี้คือ ZIP การอ่านจึงเป็นการ "แกะ ZIP ที่ไม่น่าไว้ใจ"

ป้องกันระเบิดบีบอัดสามชั้น:

1. จำนวนรายการไม่เกิน 2,000
2. ขนาดรวมหลังคลายบีบอัดไม่เกิน 128 MB (และรายการเดียวไม่เกิน 32 MB)
3. อัตราขยายตัวต่อรายการไม่เกิน 200 เท่า

ตรวจจาก**สารบัญของ ZIP ก่อน** จึงปฏิเสธได้ตั้งแต่ก่อนคลายบีบอัดจริง

**ไม่ใช้ตัวแยก XML เต็มรูปแบบโดยตั้งใจ** - ตัวแยกที่รองรับ entity ภายนอกเปิดช่องให้เกิด XXE
และระเบิดเอนทิตี ที่นี่ตัดแท็กทิ้งตรง ๆ แล้วแปลงเฉพาะเอนทิตีมาตรฐานห้าตัวกับเลขอ้างอิงอักขระ

เซลล์ที่เป็นสูตรใน XLSX อ่านจาก**ค่าที่ Excel คำนวณและเก็บไว้แล้ว** ไม่มีการประเมินสูตรใด ๆ

### PDF

**เขียนเอง ไม่ใช้ไลบรารีภายนอก** - นี่เป็นการตัดสินใจที่ตั้งใจ

PDF เป็นชนิดไฟล์ที่อันตรายที่สุดที่ระบบนี้รับ มันมีสคริปต์ฝังได้ มีการกระทำเมื่อเปิดไฟล์ได้
และมีการอ้างอิงทรัพยากรภายนอกได้ ไลบรารีที่อ่าน PDF ส่วนใหญ่มีความสามารถมากเกินกว่าที่งานนี้ต้องการมาก
การพาโค้ดเหล่านั้นเข้ามาเพื่อดึงข้อความอย่างเดียวคือการเพิ่มพื้นที่โจมตีโดยไม่จำเป็น

ตัวสกัดทำแค่สามอย่าง: หาสตรีมเนื้อหา → คลายบีบอัดด้วย `zlib` → อ่านตัวดำเนินการข้อความ (`Tj` `TJ` `'` `"`)
แล้วแปลงรหัสผ่านตาราง `ToUnicode` ที่ฝังอยู่ในไฟล์

**ขอบเขตที่รู้และยอมรับ:**

- รองรับสตรีมที่ไม่บีบอัดและ `FlateDecode` เท่านั้น (ครอบคลุม PDF ส่วนใหญ่ในทางปฏิบัติ)
- ข้อความที่ไม่ใช่ ASCII เช่นภาษาไทย **ต้องมีตาราง ToUnicode** อยู่ในไฟล์
  ถ้าไม่มี จะคืนค่าว่างแทนการเดา - **ข้อความที่เดาผิดแย่กว่าการไม่มีข้อความ**
  เพราะมันดูเหมือนสกัดสำเร็จ และหลอกทั้งผู้ใช้และการค้นหา
- PDF ที่ใส่รหัสผ่านถูกบอกตามจริงด้วย `PDF_ENCRYPTED`
- ไฟล์เสียหายจบที่ `FAILED` โดยไม่ทำให้ตัววนงานตาย

### ไฟล์ข้อความ

ตรวจว่าเป็นข้อความจริงก่อน (ไม่มีไบต์ศูนย์ · ถอดรหัส UTF-8 ได้)
ไฟล์ไบนารีที่บังเอิญมีนามสกุล `.txt` จะไม่ถูกอ่าน มิฉะนั้นดัชนีจะเต็มไปด้วยอักขระขยะ

## ข้อความที่สกัดได้เป็นข้อมูลลับ

มีความลับเท่ากับตัวเอกสารต้นทาง

**ห้าม** บันทึกลง log · ส่งออกไปยังบริการภายนอก · ใส่ใน debug trace · คืนให้ผู้ที่ไม่มีสิทธิ์เห็นเอกสารนั้น

`errorCode` ที่บันทึกไว้เป็นรหัสสั้น ๆ เท่านั้น ไม่มีชื่อไฟล์ เส้นทาง หรือเนื้อหา

## เครื่องมือของผู้ดูแล

```
GET  /api/admin/search-index                    สถานะคิว
POST /api/admin/search-index/reindex/:id        ทำใหม่หนึ่งไฟล์
POST /api/admin/search-index/reindex-all        เข้าคิวทั้งระบบ
POST /api/admin/search-index/retry-failed       ลองใหม่เฉพาะที่ไม่ถาวร
```

ทั้งหมดต้องมีสิทธิ์ `system:settings:manage` - **ผู้ใช้ทั่วไปสั่งทำดัชนีทั้งระบบไม่ได้**

`reindex-all` **เข้าคิวเท่านั้น ไม่ทำงานทันที** การทำดัชนีทั้งระบบพร้อมกันจะกินทรัพยากรจนกระทบการใช้งานจริง

สถานะคิวไม่มีเส้นทางจริง ไม่มีชื่อไฟล์ และไม่มีข้อความของเอกสารใด ๆ

`retry-failed` ข้ามความล้มเหลวถาวร - ไม่วนลองชนิดที่ไม่รองรับไปเรื่อย ๆ

## การสำรองและกู้คืน

แถวดัชนีอยู่ในฐานข้อมูล จึงติดไปกับชุดสำรองตามปกติโดยไม่ต้องทำอะไรเพิ่ม

**แต่การกู้คืนต้องไม่ขึ้นกับมัน** หลังกู้คืน ถ้าแถวดัชนีหายหรือไม่ครบ:

- ไฟล์ทุกไฟล์ยังเปิดและดาวน์โหลดได้ตามปกติ
- ค้นจากชื่อไฟล์ แท็ก และหมายเหตุยังได้เหมือนเดิม
- รอบกู้คืนตอนเริ่มระบบจะสร้างแถวที่ขาดหายให้เอง หรือสั่ง `reindex-all` ก็ได้
