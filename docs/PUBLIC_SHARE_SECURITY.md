# ความปลอดภัยของลิงก์แชร์ภายนอก

ลิงก์เหล่านี้เป็นทางเดียวในระบบที่เปิดสู่อินเทอร์เน็ตโดยไม่ต้องเข้าสู่ระบบ
เอกสารนี้อธิบายว่าอะไรกันไม่ให้มันกลายเป็นช่องโหว่

## โทเคน

| | |
|---|---|
| ความยาว | 32 ไบต์ = **256 บิต** |
| การเข้ารหัส | `base64url` (43 อักขระ ปลอดภัยใน URL) |
| แหล่งสุ่ม | `crypto.randomBytes` |
| ในฐานข้อมูล | **SHA-256 เท่านั้น** ไม่มีโทเคนดิบ |

256 บิตมากกว่าเกณฑ์ขั้นต่ำ 128 เท่าตัว เพราะโทเคนนี้ไม่มีชั้นป้องกันอื่นรองรับ:
ไม่มีชื่อผู้ใช้ ไม่มีการล็อกบัญชี ไม่มีอะไรให้ผู้โจมตีต้องผ่านก่อน
ต้นทุนของบิตที่เพิ่มมาคือความยาว URL อีกไม่กี่ตัวอักษร

### ทำไมโทเคนใช้ SHA-256 แต่รหัสผ่านใช้ bcrypt

ไม่ใช่ความไม่สม่ำเสมอ แต่เป็นการเลือกที่ต่างกันเพราะปัญหาต่างกัน:

- **รหัสผ่าน** มาจากมนุษย์ จึงมีเอนโทรปีต่ำและเดาได้ ต้องใช้แฮชที่ **ช้า**
  เพื่อให้การไล่เดาแพงเกินคุ้ม → bcrypt
- **โทเคน** สุ่มมา 256 บิต การไล่เดาไม่มีทางสำเร็จไม่ว่าแฮชจะเร็วแค่ไหน
  ในทางกลับกัน แฮชที่ช้าอย่าง bcrypt ให้ค่าต่างกันทุกครั้ง จึงค้นด้วยดัชนีไม่ได้
  และจะบังคับให้ต้องสแกนทั้งตารางทุกคำขอ → SHA-256

### สิ่งที่ไม่เคยอยู่ใน URL

รหัสทรัพยากร · `storageKey` · เส้นทางไฟล์ · checksum · id ของแถวลิงก์

โทเคนเป็นสิ่งเดียวที่ให้สิทธิ์ และการครอบครองโทเคนให้สิทธิ์เท่าที่เขียนไว้บนแถวนั้นเท่านั้น

## ความลับที่ไม่มีทางออกจากเซิร์ฟเวอร์

```
โทเคนดิบ (ยกเว้นคำตอบตอนสร้างครั้งเดียว)
tokenHash · passwordHash · รหัสผ่านดิบ
storageKey · เส้นทางไฟล์จริง
```

`toShareDto` เป็นทางออกเดียวของข้อมูลลิงก์ ทั้งแผงของผู้สร้างและหน้าผู้ดูแลใช้ตัวเดียวกัน
จึงไม่มีเส้นทางที่สองที่อาจเผลอปล่อยความลับ หน้าจอรู้ได้แค่ `passwordProtected: boolean`

มีชุดทดสอบค้นคำเหล่านี้ในคำตอบของ API รายการของผู้ดูแล บันทึกกิจกรรม และไฟล์ CSV ที่ส่งออกจริง

### ในบันทึกกิจกรรม

metadata ที่บันทึกมีเพียง `shareLinkId`, `allowPreview`, `allowDownload`,
`hasAccessCode`, `expiresAt`, เพดานและตัวนับ

ฟิลด์บอกว่ามีรหัสผ่านหรือไม่ ตั้งชื่อว่า **`hasAccessCode`** ไม่ใช่ `passwordProtected`
โดยตั้งใจ - ชั้นกันความลับของ F17 ปฏิเสธทุกคีย์ที่มีคำว่า `password`/`hash`/`token`
อยู่ข้างในไม่ว่าค่าจะเป็นอะไร ซึ่งถูกต้องแล้ว กฎที่ยอมยกเว้นให้กรณีที่ "ปลอดภัยแน่นอน"
คือกฎที่วันหนึ่งจะยกเว้นให้กรณีที่ไม่ปลอดภัยด้วย จึงเปลี่ยนชื่อฟิลด์แทนการผ่อนกฎ

## การกันหลุดขอบเขต (IDOR)

โฟลเดอร์ที่แชร์ตรวจด้วยการ **ไต่สายบรรพบุรุษที่เซิร์ฟเวอร์**: จาก id ที่ขอมา
ขึ้นไปหาแม่ทีละชั้นจนกว่าจะเจอรากของลิงก์ ไม่เจอ = ไม่พบ

ไม่ใช้เส้นทางแบบข้อความเป็นเกณฑ์ เพราะเส้นทางเปลี่ยนเมื่อมีคนย้ายโฟลเดอร์
ส่วน id ไม่เปลี่ยน ลิงก์จึงรอดจากการจัดระเบียบภายในโดยไม่ต้องทำอะไร

ชุดทดสอบบังคับครอบคลุม: ลูกโดยตรง · ลูกที่ลึกลงไป · ทรัพยากรนอกกิ่ง ·
โฟลเดอร์เหนือราก · ลิงก์ของไฟล์ที่ถูกใช้เปิดไฟล์อื่น

## รหัสผ่านและการจำกัดอัตรา

| เส้นทาง | เพดาน |
|---|---|
| ตรวจรหัสผ่าน | **10 ครั้ง / 5 นาที** ต่อ (IP + โทเคน) |
| เส้นทางแขกอื่น ๆ | 120 ครั้ง / นาที ต่อ IP |

นับแยกตามโทเคน เพื่อไม่ให้คนที่ยิงลิงก์หนึ่งไปกระทบผู้ใช้ลิงก์อื่น

หน้าจอตอบข้อความเดียวกัน (`รหัสผ่านไม่ถูกต้อง`) ทั้งกรณีรหัสผิดและกรณียิงถี่เกินไป
- ถ้าบอกว่า "ลองมากเกินไป" ผู้ที่ไล่เดาจะรู้ทันทีว่าต้องรอแล้วยิงต่อ

การใส่รหัสผิดถูกบันทึกเป็น `PUBLIC_SHARE_PASSWORD_FAILED`

## หัวข้อความปลอดภัยของเส้นทางแขก

| Header | ค่า | เหตุผล |
|---|---|---|
| `Referrer-Policy` | `no-referrer` | โทเคนอยู่ใน URL ถ้าหน้ามีลิงก์ออกนอก เบราว์เซอร์จะแนบ URL เต็มไปเป็น Referer แล้วโทเคนจะไปโผล่ใน log ของเว็บอื่น |
| `Cache-Control` | `private, no-store` | เนื้อหาส่วนตัวที่บังเอิญไม่ต้องล็อกอิน proxy สาธารณะที่เก็บไว้จะเสิร์ฟให้คนถัดไปโดยไม่ผ่านการตรวจโทเคน |
| `X-Robots-Tag` | `noindex, nofollow` | ลิงก์ที่หลุดไปอยู่ในผลค้นหาคือลิงก์ที่ทุกคนเปิดได้ |
| `X-Content-Type-Options` | `nosniff` | มาจาก `sendFile` เดิม |

หน้าของแขกใส่ `<meta name="robots">` ด้วย เพราะเครื่องมือบางตัวอ่านเฉพาะ meta ในเอกสาร

## ไม่มีทรัพยากรจากภายนอก

หน้าของแขกไม่โหลดสคริปต์ ฟอนต์ หรือรูปจากโดเมนอื่นเลย
โดยเฉพาะ **ไม่มีเครื่องมือวิเคราะห์ใด ๆ** ที่จะได้เห็น URL ที่มีโทเคนอยู่ข้างใน

การส่ง URL ของหน้าไปยังบริการภายนอกเพื่อดูสถิติ เท่ากับมอบกุญแจให้บริษัทที่สาม

## CORS และ CSP

**ไม่มีการผ่อน CORS ทั่วระบบเพื่อลิงก์แชร์** หน้าของแขกอยู่บนโดเมนเดียวกับ API
จึงเป็นคำขอ same-origin ตามปกติ นโยบายเดิมยังคงเดิมทุกประการ

## การส่งไฟล์

เนื้อหาและการดาวน์โหลดผ่าน `sendFile` **ตัวเดียวกับทุกเส้นทางในระบบ**
ไม่มีการอ่านไฟล์ดิบจากดิสก์ในเส้นทางสาธารณะ ผลที่ได้มาฟรี:

- รองรับ HTTP Range เหมือนเดิม
- `Content-Disposition` ที่กัน header injection และรองรับชื่อไฟล์ภาษาไทย
- `storageKey` ไม่เคยออกจากเซิร์ฟเวอร์

## XSS

ชื่อไฟล์และชื่อโฟลเดอร์ที่ผู้ใช้ตั้งเองปรากฏบนหน้าของแขก ทุกค่าถูกแสดงผ่าน
children ของ React จึงเป็นข้อความล้วนเสมอ ไม่มี `dangerouslySetInnerHTML` ที่ใดในหน้านี้

## การจองโควตาแบบอะตอมมิก

การตรวจแล้วค่อยเพิ่มในสองคำสั่งแยกกันจะพังเมื่อมีคำขอพร้อมกัน: ทั้งคู่อ่านเห็น
`downloadCount = 4` จากเพดาน 5 ทั้งคู่ผ่านการตรวจ แล้วทั้งคู่ก็ดาวน์โหลด → 6 ครั้งจาก 5

วิธีที่ใช้คือให้ฐานข้อมูลตรวจและเพิ่มในคำสั่งเดียว - เพดานอยู่ใน `WHERE` ของ `UPDATE`
ถ้าไม่มีแถวไหนถูกแก้ แปลว่าโควตาหมด ฐานข้อมูลล็อกแถวให้เอง ผู้ชนะจึงมีคนเดียวเสมอ

เงื่อนไขเดียวกันนั้นตรวจ `revokedAt` และ `expiresAt` ไปพร้อมกัน
ลิงก์ที่ถูกยกเลิกระหว่างที่ผู้ใช้กดปุ่มจึงหยุดก่อนไบต์แรกออกไป

มีชุดทดสอบยิงห้าคำขอพร้อมกันในโควตาที่เหลือหนึ่ง แล้วยืนยันว่าผ่านเพียงหนึ่ง

## การกู้คืน

`tokenHash` และ `passwordHash` อยู่ในชุดสำรอง หลังกู้คืนระบบ
**ลิงก์ที่ส่งให้ลูกค้าไปแล้วยังใช้ได้** ซึ่งเป็นพฤติกรรมที่ตั้งใจ - ลูกค้าไม่ได้ทำอะไรผิด

ผลที่ต้องรู้ตัว: ถ้ากู้คืนไปยังจุดก่อนที่จะมีคนกดยกเลิกลิงก์ **ลิงก์นั้นจะกลับมาใช้ได้อีก**
การกู้คืนจึงต้องตามด้วยการทบทวนรายการลิงก์ที่เปิดอยู่ที่ `/admin/public-shares`
