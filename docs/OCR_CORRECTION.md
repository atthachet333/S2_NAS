# การตรวจแก้ข้อความ - รายละเอียดทางเทคนิค

> คู่มือการใช้งานอยู่ใน [OCR_REVIEW.md](OCR_REVIEW.md)

## แบบจำลองข้อมูล

การตรวจแก้ไม่ได้สร้างตารางของข้อความขึ้นมาใหม่ทั้งชุด แต่ต่อยอดจาก `ResourceSearchIndex`
ที่มีอยู่แล้วของ F12/F13 ด้วยฟิลด์เพิ่มเติมไม่กี่ตัว

| ฟิลด์ | ความหมาย |
|---|---|
| `extractedText` | **ข้อความที่มีผลใช้งาน** - ฉบับที่แก้แล้วถ้ามีการแก้ |
| `normalizedText` | รูปที่ใช้เป็นเป้าของการค้นหา คำนวณจาก `extractedText` เสมอ |
| `rawOcrText` | **ผลดิบของเครื่อง** เก็บถาวร ไม่ถูกเขียนทับด้วยการตรวจแก้ |
| `textSource` | `NATIVE_TEXT` \| `OCR` \| `HUMAN_CORRECTED` |
| `correctedById` / `correctedAt` | ผู้ที่แก้ล่าสุดและเวลา |
| `correctionRevision` | เลขรุ่น เริ่มที่ `0` (ยังไม่เคยแก้) |

การเลือกให้ `extractedText` เป็น "ข้อความที่มีผล" แทนที่จะเพิ่มคอลัมน์ `correctedText`
แยกออกมา ทำให้ทุกจุดที่ค้นหาอยู่แล้วได้ข้อความที่ถูกต้องทันทีโดยไม่ต้องแก้อะไร
และไม่มีทางที่โค้ดสักที่จะลืมเลือกคอลัมน์ที่ถูก - ปัญหาที่เกิดแน่นอนถ้าแยกสองคอลัมน์

### `ResourceTextCorrection` - ประวัติ

หนึ่งแถวต่อการกด "บันทึก" หนึ่งครั้ง ไม่ใช่ต่อการพิมพ์หนึ่งตัวอักษร ประวัติจึงมีความหมาย

```
@@unique([resourceSearchIndexId, revision])
```

กันการบันทึกซ้ำจากการกดสองครั้ง และทำให้เลขรุ่นเป็นลำดับที่เชื่อถือได้

`onDelete: Cascade` จาก `ResourceSearchIndex` - ลบทรัพยากรถาวรแล้วประวัติหายตามไปด้วย
ไม่มีแถวกำพร้าค้างในฐานข้อมูล

### provenance ไม่ใช่ boolean

`HUMAN_CORRECTED` เป็นค่าใน enum ของ `SearchTextSource` ไม่ใช่ฟิลด์ `isCorrected: boolean`

เหตุผลคือ "ข้อความนี้มาจากไหน" มีคำตอบมากกว่าสองแบบและจะมีมากขึ้นอีกในอนาคต
boolean ตอบได้แค่ "แก้แล้ว/ยังไม่แก้" ซึ่งจะพังทันทีที่มีที่มาแบบที่สี่

การเปลี่ยน enum ครั้งนี้เป็นการ **เพิ่มค่า** ไม่ใช่การเปลี่ยนชื่อค่าเดิม
แถวเดิมทุกแถวจึงคงค่าไว้ครบ ไม่มีข้อมูลหาย (ดู `migration.sql` ของ
`20260904190000_phase_f14_text_correction`)

## การกันการเขียนทับกันเอง

ใช้การล็อกแบบมองโลกในแง่ดีผ่าน `correctionRevision`

```ts
await tx.resourceSearchIndex.updateMany({
  where: { id: index.id, correctionRevision: input.expectedRevision },
  data: { /* ... */ correctionRevision: nextRevision },
});
if (updated.count === 0) throw new AppError('OCR_CORRECTION_CONFLICT', ..., 409);
```

หน้าจออ่านเลขรุ่นตอนเปิดฟอร์ม แล้วส่งกลับมาตอนบันทึก ถ้าไม่ตรงแปลว่ามีคนแทรกเข้ามา

การเขียนและการบันทึกประวัติอยู่ใน transaction เดียวกัน การบันทึกที่ถูกปฏิเสธจึงไม่ทิ้ง
รุ่นค้างไว้ในประวัติ

**ห้ามใช้การล็อกแบบมองโลกในแง่ร้าย** (จองสิทธิ์แก้ไขไว้ล่วงหน้า) - ผู้ใช้ที่ปิดแท็บทิ้ง
จะทำให้เอกสารถูกล็อกค้างโดยไม่มีใครปลดได้ ซึ่งแย่กว่าการชนกันนาน ๆ ครั้ง

## การอ่านซ้ำต้องไม่ลบงานของคน

ทั้ง `runOcrJob` (OCR) และ `runJob` (สกัดปกติ) ตรวจ `correctionRevision > 0` ก่อนเขียน

เมื่อมีการตรวจแก้อยู่:
- ผลรอบใหม่ถูกเก็บลง `rawOcrText` **เสมอ**
- `extractedText` / `normalizedText` / `textSource` **ไม่ถูกแตะ**
- หน้าจอแสดงว่ามีผลรอบใหม่รอเทียบอยู่ (`rawTextDiffersFromCorrection`)

ผู้ใช้จึงเห็นผลใหม่และตัดสินใจเอง เครื่องไม่มีสิทธิ์ลบงานของคนทิ้งเงียบ ๆ
เพียงเพราะมันทำงานอีกรอบ

**เวอร์ชันใหม่ของไฟล์เป็นคนละแถว** (`resourceVersionId` เป็น unique) และ
`correctionRevision` ของแถวใหม่เริ่มที่ศูนย์เสมอ การตรวจแก้จึงไม่ตามไปเวอร์ชันใหม่
โดยอัตโนมัติ - v2 เป็นเอกสารคนละฉบับ ข้อความของ v1 ไม่ใช่ความจริงของมัน

## การทำความสะอาดข้อความ

`normalizeCorrection()` ต่างจาก `cleanExtractedText()` ที่ใช้กับข้อความของเครื่อง

| | เครื่องสกัดมา | คนพิมพ์เอง |
|---|---|---|
| ยุบช่องว่างซ้ำ | ✅ | ❌ |
| คงการขึ้นบรรทัด | ✅ (หนึ่งชั้น) | ✅ (ตามที่พิมพ์) |
| ตัดอักขระควบคุม | ✅ | ✅ (ยกเว้น `\n` `\t`) |
| NFC | ✅ | ✅ |

คนจัดย่อหน้าและเว้นวรรคอย่างไรก็ต้องได้อย่างนั้น การยุบช่องว่างของเขาทิ้ง
คือการลบงานที่เขาเพิ่งทำ

NFC จำเป็นเพราะ `normalizeForSearch()` ทำ NFC เหมือนกัน ถ้าข้อความที่เก็บอยู่คนละรูป
คำที่ผู้ใช้พิมพ์จะไม่มีวันตรงกับข้อความที่เก็บไว้ แม้จะเป็นคำเดียวกัน

## ลำดับผลการค้นหา

```
ชื่อตรงทั้งชื่อ (0) > ขึ้นต้นด้วย (1) > ชื่อมีคำค้น (2) > แท็ก (3) > หมายเหตุ (4)
  > HUMAN_CORRECTED (5) > NATIVE_TEXT (6) > OCR (7)
```

ข้อความที่คนตรวจแก้แล้วอยู่เหนือข้อความที่สกัดจากไฟล์โดยตรง เพราะมีคนอ่านเอกสาร
ด้วยตาแล้วยืนยันว่าถูกต้อง ซึ่งเป็นหลักฐานที่หนักแน่นกว่าการสกัดของเครื่องทุกชนิด

ตัวอย่างข้อความ (snippet) ตัดมาจาก `extractedText` จึงมาจากฉบับที่แก้แล้วโดยอัตโนมัติ

## API

ทุกเส้นทางอยู่หลัง `requireInternal` - ผู้ใช้ภายนอกเข้าไม่ถึงเลย

| Method | Path | สิทธิ์ | คืนอะไร |
|---|---|---|---|
| `GET` | `/api/resources/:id/ocr-text` | เปิดดูไฟล์ได้ | ข้อความ ผลดิบ สถานะ `canEdit` |
| `PUT` | `/api/resources/:id/ocr-text` | แก้ไขไฟล์ได้ | เลขรุ่นใหม่ |
| `DELETE` | `/api/resources/:id/ocr-text` | แก้ไขไฟล์ได้ | `{ reset }` |
| `GET` | `/api/resources/:id/ocr-text/history` | เปิดดูไฟล์ได้ | ใครแก้เมื่อไร (ไม่มีตัวข้อความ) |

`PUT` รับ `{ text, expectedRevision }` แบบ `.strict()` - ฟิลด์แปลกปลอมถูกปฏิเสธ

ด่านสิทธิ์คือ `getResource()` ตัวเดียวกับที่ทุกเส้นทางของทรัพยากรใช้ ไม่มีการเขียน
กติกาสิทธิ์ชุดใหม่ขึ้นมาสำหรับ F14 โดยเฉพาะ - กติกาสิทธิ์ที่มีสองชุดจะเพี้ยนจากกันเสมอ
เมื่อชุดหนึ่งถูกแก้

`canEdit` ของระบบนับ `isLocked` อยู่แล้ว ไฟล์ที่ถูกล็อกจึงตรวจแก้ไม่ได้โดยอัตโนมัติ

### รหัสข้อผิดพลาด

| รหัส | HTTP | ความหมาย |
|---|---|---|
| `OCR_CORRECTION_CONFLICT` | 409 | มีคนบันทึกแทรกเข้ามา |
| `OCR_CORRECTION_DENIED` | 403 | ไม่มีสิทธิ์แก้ไข หรือไฟล์ถูกล็อก |
| `OCR_CORRECTION_EMPTY` | 400 | ข้อความว่าง (ให้ใช้ปุ่มยกเลิกแทน) |
| `OCR_TEXT_NOT_FOUND` | 404 | ยังไม่มีข้อความให้แก้ |

## ความปลอดภัย

**ข้อความล้วนเท่านั้น** ตัวแก้ไขเป็น `<textarea>` ไม่ใช่ `contentEditable`
และไม่มีจุดใดในหน้าจอที่ใช้ `dangerouslySetInnerHTML` - มีชุดทดสอบสแกนซอร์สทั้งโปรเจกต์
เพื่อยืนยันข้อนี้ทุกครั้งที่รันเทส

เหตุผลไม่ใช่ทฤษฎี: ถ้าเอกสารที่สแกนมามีคำว่า `<script>` อยู่ในภาพ OCR จะอ่านมันมา
เป็นข้อความตรง ๆ และถ้าหน้าจอเอาไปใส่ `innerHTML` มันจะกลายเป็นสคริปต์ที่รันจริง
ในเบราว์เซอร์ของทุกคนที่เปิดไฟล์นั้น

**ไม่มีข้อความใน audit log** บันทึกเก็บเพียง `correctionRevision`, `characterCount`
และ `truncated` เพราะ audit log ถูกอ่านโดยคนกลุ่มที่กว้างกว่าคนที่เห็นเอกสารนั้นได้

**ประวัติไม่คืนตัวข้อความ** คืนแค่ว่าใครแก้เมื่อไร ยาวเท่าไร - สิ่งที่ต้องตอบคือ
ความรับผิดชอบ ไม่ใช่การเปิดคลังข้อความหลายชุดให้รั่วได้หลายทาง
