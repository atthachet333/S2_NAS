# การค้นหาจากเนื้อในเอกสาร (Content-aware search)

เฟส F12 ทำให้ผู้ใช้ค้นเอกสารจาก "สิ่งที่อยู่ข้างในไฟล์" ได้ ไม่ใช่จากชื่อไฟล์อย่างเดียว

ตัวอย่างที่เป็นเหตุผลของทั้งเฟสนี้:

```
ค้นหา:      ภ.ง.ด.53
ชื่อไฟล์:    เอกสารเดือนกันยายน.pdf     ← ไม่มีคำที่ค้นเลย
เนื้อในไฟล์: แบบแสดงรายการ ภ.ง.ด.53 …   ← มี
ผลลัพธ์:     เจอ พร้อมข้อความตัวอย่างรอบคำที่ตรงกัน
```

## สิ่งที่ค้นได้

การค้นหาหนึ่งครั้งดูทั้งห้าอย่างพร้อมกัน: **ชื่อไฟล์ · แท็ก · หมายเหตุ · เนื้อในเอกสาร** (และตัวกรองอื่นตามเดิม)
หนึ่งทรัพยากรให้ผลลัพธ์เพียงรายการเดียวเสมอ ไม่ใช่รายการละหนึ่งฟิลด์ที่ตรงกัน

การค้นจากชื่อไฟล์ทำงานเหมือนเดิมทุกประการ - การค้นเนื้อหาเป็นการ**เพิ่ม** ไม่ใช่การแทนที่

## ชนิดไฟล์ที่รองรับ

| กลุ่ม | นามสกุล |
|---|---|
| ข้อความ | `txt` `csv` `tsv` `json` `xml` `md` `markdown` `log` `yml` `yaml` `ini` `sql` |
| เอกสารสำนักงาน | `docx` `xlsx` `pptx` |
| เอกสารพกพา | `pdf` (เฉพาะที่มีข้อความฝังอยู่จริง) |

**ไม่รองรับ** และถูกบันทึกเป็น `UNSUPPORTED` อย่างตรงไปตรงมา: รูปภาพ วิดีโอ เสียง ไฟล์บีบอัด ไฟล์ไบนารีทั่วไป

**ไฟล์ที่มีมาโครถูกกันออกโดยตั้งใจ** (`docm` `xlsm` `pptm` `dotm` `xltm` `potm`)
แกะได้ในทางเทคนิค แต่การประกาศว่า "รองรับ" ไฟล์ที่มีโค้ดฝังอยู่เชิญให้คนถือว่ามันปลอดภัยกว่าที่เป็นจริง

## เอกสารสแกน

PDF ที่เป็นภาพสแกนล้วนไม่มีข้อความให้สกัดตามปกติ และถูกบันทึกเป็น `NO_TEXT`

สถานะ `NO_TEXT` แปลว่า "ไฟล์ถูกต้อง แต่ไม่มีข้อความข้างใน" ไม่ใช่ "อ่านไม่สำเร็จ"
ผู้ดูแลจึงแยกได้ว่าไฟล์ไหนควรใช้ OCR และไฟล์ไหนเสียจริง

> ตั้งแต่ F13 เอกสารเหล่านี้อ่านได้ด้วย OCR **เมื่อมีคนสั่ง** - ไม่เกิดขึ้นเองอัตโนมัติ
> ดู [OCR.md](OCR.md)

## การค้นภาษาไทย และเหตุผลที่ไม่ใช้ FULLTEXT

MariaDB FULLTEXT ตัดคำด้วยช่องว่างและเครื่องหมายวรรคตอน ซึ่งเป็นสมมติฐานของภาษาที่มีช่องว่างระหว่างคำ

ภาษาไทยเขียนติดกันทั้งประโยค ทั้งประโยคจึงกลายเป็น "คำ" เดียวในสายตาของ FULLTEXT
ผลคือค้น `ภาษี` จะ**ไม่เจอ** `ใบกำกับภาษี` ซึ่งเป็นสิ่งที่ผู้ใช้คาดหวังที่สุด

ระบบนี้จึงใช้การหาข้อความย่อย (`LIKE '%คำ%'`) บนคอลัมน์ `normalizedText` ที่ปรับรูปแบบไว้แล้ว
ให้ผลถูกต้องทั้งไทยและอังกฤษ

**ราคาที่ต้องจ่าย อย่างตรงไปตรงมา:** `LIKE '%คำ%'` ใช้ดัชนีไม่ได้ จึงเป็นการไล่อ่านแถว
ระบบนี้เป็นพื้นที่เก็บเอกสารขององค์กรเดียว จำนวนแถวอยู่ในหลักหมื่น และผลลัพธ์ถูกจำกัดที่ 500 รายการต่อคำค้น
จึงยอมรับได้ ถ้าปริมาณโตขึ้นมาก ทางแก้คือ n-gram parser ของ MariaDB หรือดัชนีคำแยกต่างหาก
**ไม่ใช่**การถอยไปใช้ FULLTEXT ปกติ ซึ่งจะทำให้การค้นภาษาไทยผิดตั้งแต่ต้น

การปรับรูปแบบข้อความ (ทั้งเนื้อหาและคำค้นผ่านฟังก์ชันเดียวกัน):
NFC · ตัวพิมพ์เล็กสำหรับภาษาอังกฤษ · ยุบช่องว่าง

**ห้ามตัดอักขระที่ไม่ใช่ ASCII ทิ้ง** นั่นจะลบภาษาไทยทั้งหมด และ**ห้ามถอดวรรณยุกต์หรือสระ**
"ภาษี" กับ "ภาษ" ไม่ใช่คำเดียวกัน

## ความถูกต้องตามเวอร์ชัน

ดัชนีเก็บ **หนึ่งแถวต่อหนึ่งเวอร์ชัน** และการค้นหาปกติเทียบ `versionNumber = Resource.currentVersion` เสมอ

```
v1 มี "ALPHA-ONE"          → ค้น ALPHA-ONE เจอ
v2 เอาออก ใส่ "BRAVO-TWO"  → ค้น ALPHA-ONE ไม่เจอแล้ว · ค้น BRAVO-TWO เจอ
```

แถวของเวอร์ชันเก่ายังอยู่เพื่อการตรวจสอบย้อนหลัง แต่ไม่มีทางถูกคืนเป็นผลลัพธ์ปัจจุบัน

## การจัดลำดับและเหตุผลที่ตรงกัน

ลำดับตั้งใจให้เรียบง่ายและอธิบายได้ ไม่ใช่ระบบให้คะแนนความเกี่ยวข้องเต็มรูปแบบ:

```
ชื่อตรงทั้งชื่อ > ชื่อขึ้นต้นด้วยคำค้น > ชื่อมีคำค้น > แท็ก > หมายเหตุ > เนื้อหา
```

ทุกผลลัพธ์มีป้ายบอกว่าทำไมถึงขึ้นมา: `ตรงกับชื่อไฟล์` `ตรงกับแท็ก` `ตรงกับหมายเหตุ` `ตรงกับเนื้อหาเอกสาร`

การค้นหาที่อธิบายตัวเองได้คือการค้นหาที่ผู้ใช้เชื่อถือ - โดยเฉพาะเมื่อคำค้นไม่ปรากฏในชื่อไฟล์เลย

## ตัวอย่างข้อความ (snippet)

ผลที่ตรงเพราะเนื้อหาจะมีข้อความสั้น ๆ รอบคำที่ตรงกัน จำกัดที่ 200 ตัวอักษร มีจุดไข่ปลาเมื่อถูกตัด

**ความปลอดภัยของการแสดงผล:** เซิร์ฟเวอร์คืน**ข้อความล้วน** ไม่มีแท็กและไม่มีเครื่องหมายไฮไลต์
การเน้นคำทำที่หน้าจอด้วยการตัดข้อความเป็นชิ้น ๆ แล้วให้ React วาดแต่ละชิ้นเป็นโหนดข้อความ

**ไม่มีการใช้ `dangerouslySetInnerHTML` กับเนื้อหาที่ผู้ใช้อัปโหลดที่ใดเลย** และมีชุดทดสอบยืนยันข้อนี้
เนื้อในเอกสารจึงไม่มีทางกลายเป็นโครงสร้างที่เบราว์เซอร์ตีความ

## สิทธิ์

### ฝั่งภายใน

เงื่อนไขสิทธิ์ถูกผูกเข้าไปใน `WHERE` ตั้งแต่ต้น ร่วมกับเงื่อนไขการจับคู่เนื้อหา
ไม่ใช่ค้นแยกแล้วรวมผลทีหลัง - **การรวมทีหลังคือจุดที่เงื่อนไขสิทธิ์มักหลุด**

ตัวอย่างข้อความถูกดึง**หลัง**การกรองสิทธิ์เสร็จแล้วเท่านั้น
เนื้อในเอกสารที่ผู้ใช้ไม่มีสิทธิ์เห็นจึงไม่เคยถูกอ่านขึ้นมาเพื่อทำ DTO

### พื้นที่ลูกค้า

การจับคู่เนื้อหาเป็นเงื่อนไขเพิ่มเติม**ภายใน**การไล่ลำดับชั้นที่เริ่มจากรากที่ได้รับสิทธิ์เท่านั้น (สถาปัตยกรรมเดิมของ F11)
เอกสารของลูกค้ารายอื่นถูกตัดออกด้วย**โครงสร้างของคำสั่ง** ไม่ใช่ด้วยการกรองทีหลัง

ยังไม่มีการตรวจสิทธิ์ทีละแถว - การเพิ่มการค้นเนื้อหาไม่ได้ทำให้ถอยกลับไปเป็น N+1

มีชุดทดสอบยืนยันว่าเอกสารสองฉบับที่มีเนื้อหา**เหมือนกันทุกตัวอักษร**แต่คนละลูกค้า ไม่รั่วข้ามกัน

### สิทธิ์ที่เปลี่ยนแปลง

สิทธิ์ที่หมดอายุ ถูกเพิกถอน และเอกสารที่ถูกย้ายไปถังขยะ หายจากผลการค้นหา**ทันที**
เพราะเงื่อนไขเหล่านี้อยู่ในคำสั่งค้นหาเอง ไม่ได้อยู่ในดัชนี

## ทรัพยากรที่เป็นลิงก์

`GOOGLE_SHEET` `GOOGLE_DOC` `GOOGLE_DRIVE` `WEB_LINK` ยังคงเป็นทรัพยากรที่ชี้ไปยัง URL ภายนอก

**เฟสนี้ไม่ไปดึงเนื้อหาจากปลายทาง** ค้นได้จากชื่อและ metadata เท่านั้น

## สิ่งที่เฟสนี้ไม่ได้ทำ

- OCR สำหรับเอกสารสแกน (เพิ่มใน F13 - ดู [OCR.md](OCR.md))
- การค้นหาเชิงความหมายหรือ vector search
- เครื่องมือค้นหาภายนอก (Elasticsearch / OpenSearch / Meilisearch / Typesense)
- การดึงเนื้อหาของลิงก์ภายนอก

ดูเพิ่ม: [SEARCH_INDEXING.md](SEARCH_INDEXING.md) สำหรับกลไกการสกัดและคิวงาน

## F13 - ข้อความจากเอกสารสแกน

เอกสารที่ไม่มีข้อความฝังอยู่ (PDF สแกน · ไฟล์ภาพ) อ่านได้ด้วย OCR **เมื่อมีคนสั่ง**
ข้อความที่ได้เข้าสู่ดัชนีเดียวกันและค้นหาได้ด้วยกติกาเดิมทุกประการ

`textSource` แยกที่มา: `NATIVE_TEXT` (ข้อความในไฟล์จริง) กับ `OCR` (เครื่องอ่านจากภาพ)
ผลจาก OCR มีป้าย `OCR` กำกับในผลการค้นหา และถูกจัดลำดับ**ต่ำกว่า**ข้อความจากไฟล์จริงเสมอ
เพราะเป็นการคาดเดา

การปรับรูปแบบข้อความไทยถูกขยายใน F13 เพื่อรองรับผลจาก OCR - ตัดช่องว่างระหว่างตัวอักษรไทย
และประกอบสระอำกลับคืน ทั้งเนื้อหาและคำค้นผ่านฟังก์ชันเดียวกันจึงบรรจบกันเสมอ
รุ่นของตัวสกัดเลื่อนเป็น `f13.1` และแถวรุ่นเก่าถูกทำใหม่เองตอนเริ่มระบบ

ดู [OCR.md](OCR.md)

## F14 - ข้อความที่ผ่านการตรวจแก้

การค้นหาใช้ **ข้อความที่มีผลใช้งาน** ซึ่งเป็นฉบับที่คนแก้แล้วเมื่อมีการแก้

ผู้ใช้จึงค้นเจอด้วยคำที่ถูกต้อง และ **ไม่เจอด้วยคำที่ OCR อ่านผิด** อีกต่อไป
ซึ่งเป็นจุดสำคัญ - ถ้าคำผิดยังค้นเจออยู่ การแก้ก็ไม่มีความหมาย

### ลำดับ

```
ชื่อไฟล์ > แท็ก > หมายเหตุ > ตรวจแก้แล้ว > ข้อความในไฟล์จริง > ผลของ OCR
```

ข้อความที่คนยืนยันแล้วอยู่เหนือข้อความที่เครื่องสกัดเอง เพราะมีคนอ่านเอกสารด้วยตา
แล้วยืนยัน ซึ่งเป็นหลักฐานที่หนักแน่นกว่าการสกัดของเครื่องทุกชนิด

### ป้ายในผลการค้นหา

| ป้าย | สี | ความหมาย |
|---|---|---|
| `ตรวจแก้แล้ว` | เขียว | มีคนอ่านด้วยตาแล้วยืนยัน |
| `OCR` | เหลือง | เครื่องเดาจากภาพ อาจผิด |
| (ไม่มีป้าย) | - | ข้อความที่ฝังอยู่ในไฟล์จริง |

สองกรณีนี้มีน้ำหนักต่างกันจึงใช้สีต่างกัน - สิ่งที่คนยืนยันแล้วไม่ควรหน้าตาเหมือนคำเตือน

ตัวอย่างข้อความ (snippet) ตัดมาจากฉบับที่แก้แล้วโดยอัตโนมัติ

## F15 - ตัวกรองขั้นสูงและมุมมองสำเร็จรูป

การค้นหาเดิมยังทำงานเหมือนเดิมทุกอย่าง - พิมพ์คำค้นแล้วกด Enter ได้ผลทันที
สิ่งที่เพิ่มคือตัวกรองที่ซ่อนอยู่จนกว่าจะมีคนกดเปิด

ตัวกรองใหม่ที่เกี่ยวกับเนื้อในเอกสาร:

| ตัวกรอง | ใช้ทำอะไร |
|---|---|
| ที่มาของข้อความ | แยกข้อความในไฟล์จริง / OCR / ที่ตรวจแก้แล้ว |
| สถานะ OCR | หาเอกสารที่ต้องใช้ OCR หรือที่อ่านไม่สำเร็จ |
| มีข้อความในเอกสาร | แยกเอกสารที่ค้นเนื้อในได้ออกจากที่ค้นไม่ได้ |
| ประเภทเอกสาร | จัดหมวดตามการใช้งานจริงขององค์กร |

ทั้งสามตัวแรกดูจากดัชนีของ **เวอร์ชันปัจจุบัน** เท่านั้น ไฟล์ที่ OCR ล้มเหลวใน v1
แล้วอัปโหลด v2 ที่อ่านได้ดี จึงไม่ค้างอยู่ในตัวกรอง "OCR ล้มเหลว"

ตัวกรองทั้งหมดอยู่บน URL จึงบุ๊กมาร์กและส่งต่อได้ และบันทึกเป็นชุดค้นหาได้

ดู [ADVANCED_SEARCH.md](ADVANCED_SEARCH.md), [SAVED_SEARCH.md](SAVED_SEARCH.md)
และ [SMART_VIEWS.md](SMART_VIEWS.md)
