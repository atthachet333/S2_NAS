# เครื่องมือค้นหาและตรวจสอบบันทึกกิจกรรม

`/admin/audit` - "บันทึกกิจกรรมและการตรวจสอบ"

## นี่ไม่ใช่ไทม์ไลน์ของไฟล์

ระบบมีสองที่ที่แสดงกิจกรรม และทั้งสองที่มีอยู่ด้วยเหตุผลคนละอย่าง

| | แท็บ "กิจกรรม" ในแผงรายละเอียด | `/admin/audit` |
|---|---|---|
| ผู้ใช้ | ทุกคนที่เห็นทรัพยากรนั้น | ผู้ที่ได้รับสิทธิ์ตรวจสอบ |
| คำถามที่ตอบ | "ไฟล์นี้เกิดอะไรขึ้นบ้าง" | "ใครทำอะไรในระบบ ช่วงไหน จากที่ไหน" |
| ขอบเขต | ทรัพยากรเดียว | ทั้งระบบ |
| IP / อุปกรณ์ | ไม่แสดง | แสดง |
| ส่งออก | ไม่มี | CSV |

`/admin/activity` เดิมยังอยู่เป็นไทม์ไลน์อย่างง่าย ส่วนหน้านี้คือเครื่องมือของผู้ตรวจสอบ

## แหล่งข้อมูล

ใช้ตาราง `activity_logs` **ตารางเดียวกับที่ทั้งระบบเขียนอยู่แล้ว** ไม่มีตารางตรวจสอบชุดที่สอง

ตารางตรวจสอบชุดที่สองจะเริ่มเพี้ยนจากของจริงในวันที่มีคนเพิ่มเหตุการณ์ใหม่แล้วอัปเดตแค่ที่เดียว
และไม่มีทางรู้ว่าชุดไหนถูก

## เพิ่มอย่างเดียว ไม่มีทางแก้

ไม่มี API และไม่มีปุ่มใดในระบบที่ **แก้ไข** หรือ **ลบ** เหตุการณ์ที่บันทึกแล้ว

เส้นทางทั้งหมดของโมดูลนี้เป็น `GET` ยกเว้น `POST /audit/export` ซึ่งไม่แตะบันทึกเดิม
แต่ **เพิ่ม** บันทึกใหม่ว่ามีการส่งออกเกิดขึ้น

บันทึกที่แก้ได้ไม่ใช่หลักฐาน

## สิทธิ์

| สิทธิ์ | ความหมาย |
|---|---|
| `system:audit:view` | เปิดหน้านี้และค้นหาได้ |
| `system:audit:export` | ส่งออกเป็นไฟล์ได้ |

เริ่มต้นให้ `SUPER_ADMIN` และ `ADMIN` ทั้งสองสิทธิ์ ซิงก์ด้วย `npm run rbac:sync`

**บัญชีลูกค้า (EXTERNAL) และบัญชีบริการ (SERVICE) เข้าไม่ถึงเลย** ไม่ว่าจะมีสิทธิ์อะไรติดมา
เพราะบันทึกนี้รวมข้อมูลว่าพนักงานคนไหนเปิดดูเอกสารของลูกค้ารายใดเมื่อไร
ซึ่งเป็นข้อมูลภายในองค์กร ไม่ใช่ของลูกค้า

การกันเป็นสองชั้น: `requireInternal` ที่เส้นทาง และ `canViewAudit` ที่บริการอีกครั้ง

## ตัวกรอง

- คำค้น (ชื่อผู้ดำเนินการ อีเมล รหัสเหตุการณ์)
- เหตุการณ์ / หมวดหมู่
- ผู้ดำเนินการ และประเภทผู้ดำเนินการ
- ทรัพยากร
- ช่วงเวลา (วันนี้ / 7 วัน / 30 วัน / เดือนนี้ / กำหนดเอง)
- เฉพาะที่ล้มเหลวหรือถูกปฏิเสธ

**การกรองเกิดที่เซิร์ฟเวอร์ทั้งหมด** ไม่มีที่ไหนที่ดึงทุกแถวมาแล้วค่อยกรองในเบราว์เซอร์
ตารางนี้โตทุกวินาที การดึงทั้งหมดมาก่อนจะพังในวันที่มีข้อมูลจริง

### ตัวกรองอยู่บน URL

ตัวกรองทุกตัวสะท้อนอยู่ใน query string และเดินทางไป-กลับได้ครบ

ผู้ตรวจสอบทำงานด้วยการส่งลิงก์ให้กัน ลิงก์ที่เปิดมาแล้วได้ผลคนละชุดคือลิงก์ที่ใช้ไม่ได้

ช่วงเวลาสำเร็จรูปถูกแปลงเป็น**วันที่จริง**ก่อนเขียนลง URL - "7 วันล่าสุด" ที่เลื่อนตามวันที่เปิด
จะทำให้สองคนดูหลักฐานคนละชุดโดยไม่มีใครรู้ตัว

## ชุดสำเร็จรูป

| ชุด | ใช้เมื่อ |
|---|---|
| การกำกับดูแล | ตรวจนโยบายการเก็บรักษาและ Legal Hold |
| การลบและการเปลี่ยนแปลงสำคัญ | สืบสวนว่าอะไรหายไป |
| การเข้าสู่ระบบ | ตรวจการเข้าถึงที่ผิดปกติ |
| กิจกรรมลูกค้า | ตอบคำถามว่าลูกค้ารายนี้ทำอะไรบ้าง |
| การดาวน์โหลด | ตรวจการนำข้อมูลออก |
| กิจกรรมไฟล์ / OCR / การแชร์ | ตามหัวข้อ |
| Backup และ Recovery | ตรวจงานสำรองและกู้คืน |

ทุกชุดคือ **ชุดตัวกรองสำเร็จรูป** ไม่ใช่ข้อมูลคนละชุด และประกอบด้วยเหตุการณ์ที่ระบบบันทึกจริงเท่านั้น

ชุดที่อ้างถึงเหตุการณ์ที่ไม่มีใครเขียนลงฐานข้อมูลจะให้ผลลัพธ์ว่างเปล่าเสมอ
ซึ่งอ่านเหมือน "ไม่มีอะไรเกิดขึ้น" ทั้งที่ความจริงคือ "เราไม่ได้บันทึกไว้"

## การแบ่งหน้า

- เรียงใหม่สุดก่อน
- 50 รายการต่อหน้าโดยปริยาย (25 / 50 / 100)
- ใช้ cursor ไม่ใช่ offset
- **ไม่มีตัวเลือก "ทั้งหมด"**

`offset` ที่หน้าลึก ๆ ทำให้ฐานข้อมูลต้องอ่านผ่านทุกแถวก่อนหน้าทิ้ง และตารางนี้มีแถวใหม่เพิ่มระหว่างที่ผู้ใช้กำลังพลิกหน้าอยู่
ทำให้เห็นรายการซ้ำหรือข้ามโดยไม่รู้ตัว

หน้าจอใช้ `hasMore` แทนการนับจำนวนทั้งหมด เพราะ `COUNT(*)` บนตารางขนาดนี้แพงกว่าการดึงข้อมูลที่แสดงจริง

## ดัชนี

ตรวจ `activity_logs` แล้ว **ไม่ต้องเพิ่มดัชนีใหม่** - ดัชนีที่มีอยู่ตรงกับรูปแบบคำสั่งค้นหาของหน้านี้พอดี:

```
(createdAt)                รายการหลักเรียงตามเวลา
(userId, createdAt)        กรองตามผู้ดำเนินการ
(action, createdAt)        กรองตามเหตุการณ์
(resourceId, createdAt)    ไทม์ไลน์ของทรัพยากร
(integrationAppId, createdAt)
```

ดัชนีที่เพิ่มโดยไม่มีคำสั่งค้นหารองรับ มีแต่ทำให้ทุกการเขียนช้าลง

## รายละเอียดเหตุการณ์

แสดง เวลา / เหตุการณ์ / ผู้ดำเนินการ / ทรัพยากร / IP / สรุปอุปกรณ์ / รายละเอียดที่ปลอดภัย

**ไม่มีการทิ้ง JSON ดิบลงหน้าจอ** ดูรายละเอียดที่ [AUDIT_EXPORT.md](AUDIT_EXPORT.md) และ
[COMPLIANCE_AUDIT.md](COMPLIANCE_AUDIT.md)

## ทางเข้า

- แผงรายละเอียดของทรัพยากร → "ดูกิจกรรมทั้งหมดของทรัพยากรนี้"
- `/admin/users` → "ดูกิจกรรม" ของผู้ใช้แต่ละคน
- `/admin/clients` → "ดูกิจกรรม" ของลูกค้าแต่ละราย

ทุกทางเข้าพาไปที่หน้าเดียวกันโดยกรองไว้ให้แล้ว **ไม่มีตารางสำเนาที่สอง**

ปุ่มเหล่านี้แสดงเฉพาะผู้ที่มีสิทธิ์เปิดหน้านั้นจริง ปุ่มที่กดแล้วเจอหน้าปฏิเสธไม่ช่วยใคร

## เหตุการณ์ที่ยังอ่านออกหลังของหายไป

ผู้ใช้ในระบบนี้ถูก **ปิดใช้งาน** ไม่ถูกลบ ผู้ดำเนินการในอดีตจึงยังหาชื่อเจอเสมอ

ทรัพยากรที่ถูกลบถาวรแล้วจะแสดงว่า **"ทรัพยากรถูกลบแล้ว"** พร้อมรหัสเดิม
ไม่ใช่ช่องว่าง เพราะ "มีคนดาวน์โหลดอะไรบางอย่างที่ตอนนี้ไม่มีแล้ว" ยังเป็นข้อเท็จจริงที่มีความหมาย

## ลิงก์แชร์ภายนอก (F18)

ชุดสำเร็จรูป **"ลิงก์แชร์ภายนอก"** รวมเหตุการณ์ทั้งเจ็ด:

| รหัส | ความหมาย |
|---|---|
| `PUBLIC_SHARE_CREATED` | สร้างลิงก์แชร์ภายนอก |
| `PUBLIC_SHARE_REVOKED` | ยกเลิกลิงก์แชร์ภายนอก |
| `PUBLIC_SHARE_ACCESSED` | แขกเปิดลิงก์แชร์ภายนอก |
| `PUBLIC_SHARE_DOWNLOADED` | แขกดาวน์โหลดผ่านลิงก์แชร์ |
| `PUBLIC_SHARE_PASSWORD_FAILED` | ใส่รหัสผ่านลิงก์แชร์ไม่ถูกต้อง |
| `PUBLIC_SHARE_EXPIRED_ACCESS_ATTEMPT` | พยายามเปิดลิงก์ที่ใช้ไม่ได้แล้ว |
| `PUBLIC_SHARE_LIMIT_REACHED` | ลิงก์ใช้สิทธิ์ครบตามที่กำหนด |

สามรายการท้ายถูกทำเครื่องหมายเป็นความล้มเหลว จึงปรากฏในตัวกรอง "เฉพาะที่ล้มเหลว/ถูกปฏิเสธ"

**ผู้ดำเนินการของเหตุการณ์ฝั่งแขกคือ "ระบบ"** เพราะไม่มีผู้ใช้จริง - แขกไม่เคยกลายเป็นบัญชี
ตัวตนที่แท้จริงคือ `shareLinkId` ในรายละเอียดเพิ่มเติม ซึ่งเป็นสิ่งเดียวที่เรารู้จริงเกี่ยวกับเขา
IP และสรุปอุปกรณ์บันทึกตามปกติผ่านคอลัมน์เดิม

การเปิดถูกนับครั้งเดียวต่อการเปิดหน้า ไม่ใช่ทุกคำขอช่วงข้อมูล บันทึกจึงไม่ถูกถมด้วยเสียงรบกวน
