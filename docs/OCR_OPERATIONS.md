# การติดตั้งและดูแล OCR

คู่มือฝั่งปฏิบัติการของ [OCR.md](OCR.md)

## การติดตั้ง

ระบบต้องการ Tesseract OCR ในเครื่องเดียวกับ backend พร้อมข้อมูลภาษาไทยและอังกฤษ

**รุ่นที่ทดสอบแล้ว: 5.4.0.20240606** (Windows, UB-Mannheim build)

ไม่ต้องใช้ Docker และการติดตั้งไม่แตะบริการอื่นในเครื่อง (MariaDB, MySQL, PM2, Cloudflare)

ตรวจว่าติดตั้งสำเร็จ:

```
tesseract --version
tesseract --list-langs
```

รายชื่อภาษาต้องมี **`tha`** และ **`eng`** ถ้าขาดอย่างใดอย่างหนึ่ง ระบบจะรายงานว่ายังไม่พร้อม
และ**ไม่**ทำ OCR ให้ - การอ่านเอกสารไทยด้วยภาษาอังกฤษอย่างเดียวได้ข้อความขยะ
ที่ดูเหมือนสำเร็จ ซึ่งแย่กว่าการบอกตรง ๆ ว่ายังไม่พร้อม

## การตั้งค่า

```
S2_NAS_OCR_ENABLED=1
S2_NAS_OCR_BIN=C:/Program Files/Tesseract-OCR/tesseract.exe
S2_NAS_OCR_LANGUAGES=tha+eng
```

| ตัวแปร | ค่าเริ่มต้น | ความหมาย |
|---|---|---|
| `S2_NAS_OCR_ENABLED` | `0` | `0` = ปิด OCR ทั้งหมด ระบบยังทำงานครบทุกอย่าง |
| `S2_NAS_OCR_BIN` | - | เส้นทางของโปรแกรม (ไม่พึ่ง PATH) |
| `S2_NAS_OCR_LANGUAGES` | `tha+eng` | ต้องมีครบในเครื่องจึงจะถือว่าพร้อม |
| `S2_NAS_OCR_MAX_PAGES` | `50` | หน้าที่เกินถูกบันทึกว่าอ่านไม่ครบ ไม่ใช่เงียบ ๆ |
| `S2_NAS_OCR_TIMEOUT_MS` | `60000` | เวลาสูงสุดต่อหนึ่งหน้า |
| `S2_NAS_OCR_CONCURRENCY` | `1` | OCR กิน CPU มาก ค่าเริ่มต้นจึงเป็นหนึ่ง |
| `S2_NAS_OCR_MAX_IMAGE_BYTES` | 32 MB | ขนาดไฟล์สูงสุด |
| `S2_NAS_OCR_MAX_PIXELS` | 80,000,000 | กันภาพที่บีบมาเล็กแต่คลายออกใหญ่มหาศาล |
| `S2_NAS_OCR_TEMP_ROOT` | temp ของระบบ | รากของไฟล์ชั่วคราว |

**ค่าที่ผิดทำให้ OCR ใช้ไม่ได้ ไม่ใช่ทำให้ระบบเริ่มไม่ได้**

## เครื่องมือบรรทัดคำสั่ง

```bash
npm run ocr:status            # สถานะเครื่องมือและคิวงาน
npm run ocr:eligible          # ไฟล์ที่น่าจะได้ประโยชน์จาก OCR
npm run ocr:run -- <resourceId>   # สั่งอ่านหนึ่งไฟล์ แล้วรอจนเสร็จ
npm run ocr:retry-failed      # ลองใหม่เฉพาะที่ล้มเหลวแบบไม่ถาวร
```

`ocr:status` **เรียกโปรแกรมจริง** ไม่ใช่แค่อ่านค่าจากไฟล์ตั้งค่า
สถานะเป็น `READY` ก็ต่อเมื่อเรียกได้จริงและมีข้อมูลภาษาครบตามที่ตั้งไว้

ตัวอย่างผลลัพธ์:

```
  เปิดใช้งาน             ใช่
  เครื่องมือ             tesseract v5.4.0.20240606
  ภาษาที่ตั้งไว้         tha+eng
  ภาษาที่มีในเครื่อง     eng, osd, tha
  สถานะ                  READY
```

CLI ใช้เซอร์วิสชุดเดียวกับ API และหน้าจอ **ไม่มีเส้นทางลัดของตัวเอง**
และรับเฉพาะรหัสทรัพยากร **ไม่รับเส้นทางจริงบนดิสก์** - เซิร์ฟเวอร์เป็นผู้แปลงเป็นเส้นทางจริงเสมอ

## เส้นทางของผู้ดูแล

```
GET  /api/admin/ocr                 สถานะเครื่องมือ + คิวงาน
GET  /api/admin/ocr/eligible        ไฟล์ที่รอการสั่ง OCR
POST /api/admin/ocr/bulk            สั่งหลายไฟล์ (สูงสุด 200 ต่อครั้ง)
POST /api/admin/ocr/retry-failed    ลองใหม่
```

ทั้งหมดต้องมีสิทธิ์ `system:settings:manage`

`bulk` **เข้าคิวเท่านั้น ไม่รอให้เสร็จ** และรายงานจำนวนที่รับกับที่ข้ามพร้อมเหตุผลตามจริง

สถานะที่คืนไม่มีเส้นทางจริง ไม่มีชื่อไฟล์ และไม่มีข้อความของเอกสารใด ๆ

## คิวงาน

OCR ใช้ **คิวเดียวกับการสกัดข้อความปกติ** แยกด้วย `jobKind` (`EXTRACT` / `OCR`)

กลไกที่ใช้ร่วมกันทั้งหมด: การจองงานแบบเปรียบเทียบและเขียนในคำสั่งเดียว ·
การกู้คืนงานค้างหลังเซิร์ฟเวอร์ล่ม · การลองใหม่แบบจำกัดจำนวน · ทำงานเก่าที่สุดก่อน

สิ่งที่แยกกัน:

- **ลำดับความสำคัญ** - การสกัดปกติทำก่อน OCR เสมอ
  งาน OCR ค้างเป็นร้อยชิ้นจึงไม่ทำให้ไฟล์ DOCX ที่เพิ่งอัปโหลดรอเป็นชั่วโมง
- **จำนวนงานพร้อมกัน** - OCR มีค่าของตัวเอง (ค่าเริ่มต้น 1)

## ความปลอดภัย

**การเรียกโปรแกรมภายนอก** ใช้ `execFile` พร้อมอาร์กิวเมนต์เป็น**อาร์เรย์**เสมอ
ไม่มี `shell: true` ที่ใดเลย คำสั่งจึงไม่ถูกตีความโดยเชลล์ และไม่มีทางเกิดการฉีดคำสั่ง
แม้ชื่อไฟล์จะเป็น `; calc.exe` หรือ `& whoami` ก็ตาม - มีชุดทดสอบยิงชื่อเหล่านี้จริง

**เส้นทางไฟล์** ที่ส่งให้เครื่องมือถูกสร้างโดยเซิร์ฟเวอร์ทั้งหมด ผ่าน `resolveStorageKey`
ซึ่งบังคับให้อยู่ในรากของพื้นที่จัดเก็บ **ผู้ใช้ไม่มีทางกำหนดเส้นทางจริงได้**
และชื่อไฟล์ของผู้ใช้ไม่เคยกลายเป็นส่วนหนึ่งของเส้นทาง

**ไฟล์ชั่วคราว** อยู่ในโฟลเดอร์ที่ชื่อสุ่มโดยเซิร์ฟเวอร์ ลบทุกครั้งใน `finally`
และโฟลเดอร์ที่ค้างเกินหนึ่งวันจากการล่มกลางคันถูกเก็บกวาดตอนเริ่มระบบ

**ข้อความที่อ่านได้มีความลับเท่ากับตัวเอกสาร** ห้ามบันทึกลง log ห้ามส่งออกนอกระบบ
และไม่ปรากฏใน audit - บันทึกมีแต่รหัสอ้างอิงและผลลัพธ์

## การสำรองและกู้คืน

ดัชนี OCR เป็น **ข้อมูลที่สร้างใหม่ได้** เหมือนดัชนีข้อความปกติ

ติดไปกับชุดสำรองเต็มตามปกติ แต่การกู้คืน**ต้องไม่ขึ้นกับมัน** หลังกู้คืน ถ้าแถวหาย:

- ไฟล์ทุกไฟล์ยังเปิดและดาวน์โหลดได้ตามปกติ
- ค้นจากชื่อไฟล์ แท็ก และหมายเหตุยังได้เหมือนเดิม
- ค้นจากเนื้อในเอกสารสแกนใช้ไม่ได้จนกว่าจะสั่ง OCR ใหม่

**ไฟล์ภาพชั่วคราวระหว่างทำ OCR ไม่ถูกสำรอง** - มันเป็นของชั่วคราวจริง ๆ และถูกลบทันทีที่อ่านเสร็จ

## เมื่อมีปัญหา

| อาการ | ตรวจ |
|---|---|
| ปุ่ม OCR ไม่ปรากฏ | `npm run ocr:status` - ต้องเป็น `READY` |
| สถานะไม่ใช่ `READY` | เส้นทางของโปรแกรม และ `tesseract --list-langs` ต้องมี `tha` |
| งานค้างอยู่นาน | ดูจำนวนคิว - OCR ทีละหนึ่งงานตามค่าเริ่มต้น |
| `OCR_RENDER_FAILED` | ภาพในเอกสารอาจใช้รูปแบบที่ยังไม่รองรับ (CCITT / JPEG2000) |
| อ่านข้อความไทยผิด | ตรวจว่าตั้ง `tha+eng` และดูคุณภาพของภาพต้นทาง |

ถ้า OCR รบกวนการทำงานของระบบ ตั้ง `S2_NAS_OCR_ENABLED=0` แล้วเปิดกลับภายหลัง -
**ไม่มีข้อมูลใดสูญหายจากการปิดมัน**
