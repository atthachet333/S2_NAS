# คิวตรวจ OCR

> การแก้ข้อความอยู่ใน [OCR_REVIEW.md](OCR_REVIEW.md) และ [OCR_CORRECTION.md](OCR_CORRECTION.md)

## "ตรวจแล้วถูก" กับ "ตรวจแล้วแก้" ไม่ใช่เรื่องเดียวกัน

นี่คือแนวคิดหลักของทั้งเฟสนี้

ผลของ OCR **ส่วนใหญ่ถูกต้องอยู่แล้ว** การบังคับให้คนแก้ข้อความก่อนถึงจะบันทึกได้
จะทำให้คนเลิกตรวจตั้งแต่เอกสารแผ่นที่สาม คิวนี้จึงรองรับการกด "ถูกต้องแล้ว"
โดยไม่ต้องแตะข้อความเลย

| การกระทำ | textSource | reviewStatus |
|---|---|---|
| ยังไม่มีใครดู | `OCR` | `UNREVIEWED` |
| ตรวจแล้วถูกต้อง | `OCR` (ไม่เปลี่ยน) | `VERIFIED` |
| แก้ข้อความ | `HUMAN_CORRECTED` | `CORRECTED` |

**การกดยืนยันต้องไม่เปลี่ยน `textSource` เป็น `HUMAN_CORRECTED`**

ไม่มีใครพิมพ์อะไรลงไป การบอกว่า "คนแก้แล้ว" ทั้งที่ไม่มีใครแก้ จะทำให้ข้อมูลที่ใช้
วัดคุณภาพ OCR ในอนาคตเป็นเท็จ และจะตอบไม่ได้ว่าเครื่องอ่านถูกเองกี่ฉบับ

## สองสถานะที่ตอบคนละคำถาม

```
SearchIndexStatus  → เครื่องอ่านสำเร็จหรือไม่   (READY / FAILED / NO_TEXT / ...)
OcrReviewStatus    → มีคนดูผลนั้นแล้วหรือยัง   (UNREVIEWED / VERIFIED / CORRECTED)
```

แยกเป็นสอง enum โดยตั้งใจ การยัดสองเรื่องนี้ลงตัวเดียวจะทำให้ตอบไม่ได้ว่างานที่
`FAILED` เคยมีคนดูแล้วหรือยัง

`FAILED` เป็นสถานะของการอ่าน **ไม่ใช่สถานะของการตรวจ**

## รายการที่เข้าคิว

- `textSource = OCR`
- `status = READY`
- `reviewStatus = UNREVIEWED`
- เวอร์ชันปัจจุบันเท่านั้น
- ไม่อยู่ในถังขยะ

เรียง **เก่าสุดก่อน** เป็นค่าเริ่มต้น - เอกสารที่รอมานานที่สุดควรได้รับการตรวจก่อน
ไม่อย่างนั้นของเก่าจะไม่มีวันถูกแตะเลย

เลือกเรียงตามความมั่นใจต่ำก่อนได้ ซึ่งมักเป็นกลุ่มที่อ่านผิดจริง

## จำนวนที่เหลือ

นับจากรายการที่ **ผู้เรียกเห็นได้จริง** เท่านั้น

การรายงานตัวเลขรวมของทั้งระบบจะทำให้ผู้ใช้เห็นว่า "เหลือ 40 รายการ" แล้วตรวจไป
สามรายการก็หมดคิว ซึ่งดูเหมือนระบบพัง

ไม่มีเปอร์เซ็นต์ความคืบหน้า เพราะไม่มีตัวหารที่มีความหมาย - เอกสารใหม่เข้าคิวได้ตลอดเวลา

## สิทธิ์

การตรวจเป็นการเปลี่ยนข้อมูลของทรัพยากร จึงใช้ **สิทธิ์แก้ไข** เป็นเกณฑ์
ซึ่งเป็นเกณฑ์เดียวกับการสั่ง OCR และการตรวจแก้ข้อความใน F14

ไฟล์ที่ถูกล็อกตรวจไม่ได้โดยอัตโนมัติ เพราะ `canEdit` นับ `isLocked` อยู่แล้ว
ผู้ใช้ยังเปิดอ่านผลได้ แต่กดยืนยันหรือแก้ไม่ได้

**ผู้ใช้ภายนอกเข้าไม่ถึงเลย** ทั้งหน้าจอ เส้นทาง API และข้อมูลผู้ตรวจ

## การข้าม

"ข้ามไปก่อน" เลื่อนไปรายการถัดไปในรอบนี้เท่านั้น **ไม่บันทึกว่าตรวจแล้ว**
เอกสารจะกลับมาอยู่ในคิวรอบหน้า ซึ่งตรงกับที่ผู้ใช้คาดหวังจากคำว่า "ข้าม"

## การแก้ข้อความ

ใช้กล่องเดิมของ F14 ทั้งหมด ไม่มีตรรกะการแก้ข้อความชุดที่สอง

`saveCorrection()` ตั้ง `reviewStatus = CORRECTED` ให้เอง เอกสารที่มีคนนั่งแก้ไปแล้ว
จึงไม่ค้างอยู่ในคิว "ยังไม่ตรวจ" และคนจะไม่ถูกเรียกให้ตรวจงานที่ตัวเองเพิ่งทำเสร็จ

## หน้าจอ

`/ocr-review` - เอกสารต้นฉบับอยู่ตรงกลาง รายการในคิวอยู่ซ้าย ข้อความและปุ่มอยู่ขวา

ปุ่มที่ใช้บ่อยที่สุดอยู่ที่เดิมทุกครั้ง ผู้ใช้จึงกดรัวได้โดยไม่ต้องหาปุ่มใหม่ทุกฉบับ
และหลังกดแล้วเลื่อนไปรายการถัดไปเอง **โดยไม่โหลดหน้าใหม่**
