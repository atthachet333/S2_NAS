# การค้นหาขั้นสูง

> ชุดค้นหาที่บันทึกไว้อยู่ใน [SAVED_SEARCH.md](SAVED_SEARCH.md)
> มุมมองสำเร็จรูปอยู่ใน [SMART_VIEWS.md](SMART_VIEWS.md)

## หลักการ

**การค้นหาแบบง่ายต้องไม่ยากขึ้นเพราะมีตัวกรองขั้นสูง**

ผู้ใช้ส่วนใหญ่พิมพ์คำค้นแล้วกด Enter แผงตัวกรองจึงถูกซ่อนไว้จนกว่าจะมีคนกดเปิด
และไม่มีตัวกรองใดที่ต้องกรอกก่อนถึงจะค้นหาได้

**ตัวกรองทำให้ผลลัพธ์แคบลงได้อย่างเดียว ไม่มีทางทำให้เห็นเอกสารเพิ่ม**

เงื่อนไขสิทธิ์ถูกใส่เข้าไปใน `WHERE` ตั้งแต่ต้นใน `searchResources()` และตัวกรอง
ทุกตัวถูกต่อท้ายอยู่ใน `AND` เดียวกัน จึงไม่มีทางที่ตัวกรองใดจะถอดเงื่อนไขสิทธิ์ออก

## ตัวกรองที่มี

| ตัวกรอง | ค่าที่เลือกได้ |
|---|---|
| ประเภทไฟล์ | PDF · รูปภาพ · Word · Excel · PowerPoint · ข้อความ · ลิงก์ · โฟลเดอร์ · อื่น ๆ |
| ไดร์ฟ | ไดร์ฟของฉัน · ไดร์ฟของระบบ |
| ประเภทเอกสาร | ตามที่ผู้ดูแลตั้งไว้ |
| ผู้ดูแล | ผู้ใช้ภายใน |
| ผู้อัปโหลด | ผู้ใช้ภายใน |
| ต้นทาง | อัปโหลดเอง · Google · S2 Payroll · S2 ERP · LINE Bot · ลูกค้าอัปโหลด · ระบบ |
| แท็ก | แท็กขององค์กร |
| ที่มาของข้อความ | ข้อความปกติ · OCR · ตรวจแก้แล้ว |
| สถานะ OCR | ยังไม่ประมวลผล · กำลังประมวลผล · พร้อมค้นหา · ต้องใช้ OCR · OCR สำเร็จ · OCR ล้มเหลว · ตรวจแล้ว |
| วันที่อัปโหลด / แก้ไข | วันนี้ · 7 วัน · 30 วัน · เดือนนี้ · กำหนดเอง |
| อื่น ๆ | มีข้อความในเอกสาร · ยังไม่มีแท็ก · ยังไม่ระบุประเภท · รายการโปรด |

### ไม่มี MIME ให้กรอก

ผู้ใช้คิดเป็น "ไฟล์ Word" ไม่ใช่
`application/vnd.openxmlformats-officedocument.wordprocessingml.document`

การจับกลุ่มทำจาก **นามสกุลไฟล์** ไม่ใช่ MIME เพราะ MIME ที่ browser ส่งมาตอนอัปโหลด
เชื่อถือไม่ได้ ส่วนนามสกุลเป็นสิ่งที่ผู้ใช้เห็นและเข้าใจตรงกัน

"อื่น ๆ" นิยามด้วย **การยกเว้น** ไม่ใช่รายชื่อนามสกุล เพราะรายชื่อจะล้าสมัยทันที
ที่มีคนอัปโหลดนามสกุลที่ไม่เคยเจอ

### ไม่มีสถานะที่แต่งขึ้น

ทุกค่าในตัวกรองสถานะ OCR สะท้อนสถานะที่ระบบรู้จริงจาก F12/F13/F14/F15
ผู้ใช้ที่กรอง "OCR ล้มเหลว" แล้วได้รายการมา ต้องกดจัดการได้จริงทุกรายการ

### วันที่คำนวณที่เซิร์ฟเวอร์

"เดือนนี้" ถูกแปลงเป็นช่วงเวลาจริงตอนค้นหา ไม่ใช่ตอนบันทึกชุดค้นหา
ชุดที่บันทึกไว้เดือนสิงหาคมจึงหมายถึงเดือนกันยายนเมื่อเปิดในเดือนกันยายน

ไม่รับช่วงเวลาที่ browser คำนวณมาให้ เพราะนาฬิกาและโซนเวลาของเครื่องผู้ใช้
เชื่อถือไม่ได้ และผลการค้นหาที่ต่างกันตามเครื่องที่ใช้เปิดคือสิ่งที่อธิบายให้ผู้ใช้ฟังไม่ได้

## ตัวกรองที่อ้างอิงเนื้อในเอกสาร

ตัวกรอง **ที่มาของข้อความ**, **สถานะ OCR** และ **มีข้อความในเอกสาร**
ดูจากดัชนีของ **เวอร์ชันปัจจุบัน** เท่านั้น

ถ้าไม่ผูกกับเวอร์ชันปัจจุบัน ไฟล์ที่ OCR ล้มเหลวใน v1 แล้วอัปโหลด v2 ที่อ่านได้ดี
จะยังโผล่ในตัวกรอง "OCR ล้มเหลว" ตลอดไป

Prisma เทียบคอลัมน์ของตารางลูกกับตารางแม่ในเงื่อนไข relation ไม่ได้
จึงใช้ SQL ตรงเหมือนที่ `contentMatchResourceIds` ทำอยู่แล้ว (ดู `indexStateResourceIds`)

## สถานะบน URL

ตัวกรองทั้งหมดอยู่บน query string

```
/search?q=ภาษี&fileKind=pdf&textSource=OCR&uploadedPreset=thisMonth&sort=newest
```

ทำให้:

- รีเฟรชแล้วไม่หาย
- บุ๊กมาร์กได้
- ส่งลิงก์ให้เพื่อนร่วมงานได้ (ผู้รับยังเห็นเฉพาะสิ่งที่ตัวเองมีสิทธิ์)
- เป็นรูปแบบเดียวกับที่ชุดค้นหาที่บันทึกไว้ใช้

รายชื่อคีย์อยู่ใน `frontend/src/lib/search-filters.ts` ที่เดียว
และตรงกับ `searchFiltersSchema` ฝั่งเซิร์ฟเวอร์

ค่าที่เป็นเท็จหรือว่างถูกลบออกจาก URL แทนที่จะเขียน `false` ลงไป URL จึงสั้นและอ่านออก

## ป้ายตัวกรองและการล้าง

ตัวกรองที่ใช้อยู่แสดงเป็นป้ายที่กดปิดได้ทีละอัน

ปุ่ม **ล้างตัวกรอง** ล้างเฉพาะตัวกรอง **ไม่ล้างคำค้น** - ผู้ใช้ที่กดปุ่มนี้กำลังบอกว่า
"ค้นคำเดิม แต่เลิกกรอง" ไม่ใช่ "เริ่มใหม่ทั้งหมด"

การเรียงลำดับไม่นับเป็นตัวกรอง จึงไม่แสดงเป็นป้ายที่กดปิดได้ - มันไม่ได้กรองอะไรออก

## การเรียงลำดับ

| ตัวเลือก | ทำงานอย่างไร |
|---|---|
| เกี่ยวข้องมากที่สุด | คำนวณหลังดึงข้อมูล (`rankOf`) - ฐานข้อมูลไม่รู้จักคำค้น |
| ล่าสุด / เก่าสุด | `updatedAt` |
| ชื่อ ก-ฮ | `normalizedName` |
| ขนาดใหญ่สุด | `size` |

"เกี่ยวข้องมากที่สุด" ไม่ถูกส่งลงฐานข้อมูล การอ้างว่าฐานข้อมูลเรียงตามความเกี่ยวข้องได้
ทั้งที่มันไม่รู้จักคำค้นเลย จะเป็นการโกหกผู้ใช้

## จำนวนผลลัพธ์

แสดงจำนวนที่ backend คืนมาจริง เมื่อผลถูกตัดตามเพดาน จะบอกว่าแสดงกี่รายการแรก
ไม่นำเสนอตัวเลขว่าเป็นยอดรวมทั้งหมดถ้าไม่ได้นับจริง
