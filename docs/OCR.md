# การอ่านข้อความจากเอกสารสแกน (OCR)

เฟส F13 เพิ่มความสามารถอ่านข้อความจากเอกสารที่ไม่มีข้อความฝังอยู่ - เอกสารสแกนและไฟล์ภาพ

```
PDF สแกน → การสกัดปกติได้ NO_TEXT → มีคนสั่ง OCR → อ่านข้อความ → ค้นหาได้ตามปกติ
```

ทั้งหมดเป็นส่วนขยายของดัชนีเดิมใน F12 **ไม่มีระบบค้นหาชุดที่สอง**

## OCR ไม่เกิดขึ้นเอง

นี่คือการตัดสินใจที่กำหนดรูปร่างของทั้งเฟสนี้

OCR ช้า กิน CPU มาก และผลลัพธ์เป็น **การคาดเดา** การไล่ทำกับทุกภาพที่อัปโหลดเข้ามา
จะเผาเวลาเครื่องไปกับโลโก้บริษัทและรูปถ่ายที่ไม่มีใครค้นหา

ระบบจึงบอกได้เพียงว่าไฟล์ไหน "น่าจะได้ประโยชน์" แล้วปล่อยให้คนตัดสินใจ
สถานะ `NO_TEXT` และ `UNSUPPORTED` ที่ F12 บันทึกไว้อยู่แล้ว คือสิ่งที่ตอบคำถามนั้นได้พอดี

## เครื่องมือ

| หัวข้อ | ค่า |
|---|---|
| เครื่องมือ | Tesseract OCR |
| รุ่นที่ทดสอบ | **5.4.0.20240606** (leptonica 1.84.1) |
| ภาษา | `tha+eng` |
| ที่ตั้ง | ในเครื่องเดียวกับที่เก็บไฟล์ |

**ไม่มีบริการภายนอกใด ๆ** ไม่ Google Vision ไม่ AWS Textract ไม่ Azure ไม่ OpenAI
**ไบต์ของเอกสารไม่เคยออกจากเครื่องนี้**

OCR เป็นความสามารถ**เสริม** ถ้าเครื่องมือไม่พร้อม S2 NAS เริ่มทำงานได้ตามปกติทุกอย่าง
และรายงาน `OCR_NOT_CONFIGURED` อย่างตรงไปตรงมา ไม่ใช่ล้มทั้งระบบ

## ไฟล์ที่เข้าเงื่อนไข

| เข้าเงื่อนไข | ไม่เข้าเงื่อนไข |
|---|---|
| PDF ที่สกัดข้อความแล้วได้ `NO_TEXT` (เอกสารสแกน) | PDF ที่มีข้อความอยู่แล้ว |
| `png` `jpg` `jpeg` `webp` `tif` `tiff` `bmp` | `docx` `xlsx` `pptx` (มีข้อความอยู่แล้ว) |
| | ไฟล์บีบอัด · วิดีโอ · เสียง · โปรแกรม |

**PDF ที่มีข้อความอยู่แล้วจะไม่ถูก OCR** การเอาข้อความที่เครื่องเดามาทับข้อความที่ถูกต้องอยู่แล้ว
คือการทำให้ผลแย่ลง ไม่ใช่ดีขึ้น

ไฟล์ที่ OCR ไปแล้วยังสั่ง "สแกนใหม่" ได้ ซึ่งเป็นการทำซ้ำบนแถวเดิม ไม่ใช่การสร้างแถวใหม่

## การอ่านเอกสารสแกน โดยไม่ใช้ตัวเรนเดอร์

ทางเลือกปกติคือเรนเดอร์หน้า PDF เป็นภาพด้วยเครื่องมือภายนอก (poppler / Ghostscript / MuPDF)

**ระบบนี้ไม่ทำแบบนั้น** ด้วยเหตุผลสองข้อ:

1. การเรนเดอร์แปลว่า "ตีความคำสั่งวาดของเอกสารที่ไม่น่าไว้ใจ" ซึ่งเป็นพื้นที่โจมตีที่กว้างมาก
2. เครื่องที่ติดตั้งระบบนี้ไม่มีเครื่องมือเหล่านั้น และ F13 ไม่ควรบังคับให้ต้องมี

เอกสารสแกนมีโครงสร้างที่ง่ายกว่านั้นมาก: แต่ละหน้าคือ **ภาพหนึ่งภาพที่ฝังอยู่ในไฟล์**
ระบบจึงดึงภาพนั้นออกมาตรง ๆ แล้วส่งให้ Tesseract อ่าน

ผลคือ **ไม่มีอะไรในระบบตีความคำสั่งวาดของ PDF เลย** ไม่รันสคริปต์ ไม่ตามลิงก์
ไม่เรียกโปรแกรมภายนอกเพื่อเรนเดอร์

### ขอบเขตที่รู้และยอมรับ

รองรับภาพที่ฝังแบบ `DCTDecode` (JPEG - เครื่องสแกนใช้เกือบทั้งหมด) และ `FlateDecode` (บิตแมปดิบ 8 บิต gray/RGB)

`CCITTFaxDecode` และ `JPXDecode` **ยังไม่รองรับ** และถูกรายงานเป็น `OCR_RENDER_FAILED` ตามจริง
ไม่ใช่บันทึกว่า "ไม่พบข้อความ" ซึ่งจะเป็นการโกหก

เอกสารที่วาดด้วยเส้นและตัวอักษรจริงจะไม่มีภาพให้ดึง - แต่เอกสารแบบนั้นมีข้อความฝังอยู่แล้ว
และถูกอ่านด้วยการสกัดปกติของ F12 ไปตั้งแต่ต้น จึงไม่เข้าเงื่อนไข OCR อยู่ดี

## ภาษาไทย

Tesseract แยกตัวอักษรไทยด้วยช่องว่างและเขียนสระอำแยกเป็นสองตัวเป็นปกติ:

```
ภาพที่มีคำว่า  ใบกำกับภาษี
Tesseract อ่านได้  "ใบ ก ํ า ก ั บ ภา ษี"
```

ถ้าเก็บแบบนั้นตรง ๆ การค้นคำว่า `กำกับภาษี` จะไม่มีวันเจอ การปรับรูปแบบข้อความ (`normalizeForSearch`)
จึงมีขั้นตอนเฉพาะของภาษาไทยสองข้อ:

1. **ตัดช่องว่างที่อยู่ระหว่างตัวอักษรไทยสองตัว** - ภาษาไทยไม่เขียนเว้นวรรคระหว่างตัวอักษรในคำเดียวกัน
   ช่องว่างแบบนั้นจึงไม่ใช่ความตั้งใจของผู้เขียน ช่องว่างระหว่างไทยกับอังกฤษยังคงอยู่
2. **ประกอบสระอำกลับคืน** - นิคหิต (U+0E4D) + สระอา (U+0E32) → สระอำ (U+0E33)
   ยูนิโคดไม่ได้กำหนดการประกอบคู่นี้ไว้ใน NFC ภาษาไทยจึงต้องจัดการเอง

**ทั้งเนื้อหาและคำค้นผ่านฟังก์ชันเดียวกัน** จึงมาบรรจบกันที่รูปแบบเดียวเสมอ

ราคาที่ต้องจ่ายอย่างตรงไปตรงมา: การเว้นวรรคระหว่าง**วลี**ไทยก็ถูกตัดไปด้วย
`ภาษี ดี` กับ `ภาษีดี` จึงเป็นข้อความเดียวกันในสายตาการค้นหา ความแม่นยำลดลงเล็กน้อย
แลกกับการที่ข้อความจาก OCR ค้นหาได้จริง - คุ้มค่า เพราะการค้นภาษาไทยเป็นการหาข้อความย่อยอยู่แล้ว

> การเปลี่ยนนี้กระทบข้อความที่ทำดัชนีไว้ก่อนหน้าด้วย รุ่นของตัวสกัดจึงถูกเลื่อนเป็น `f13.1`
> และแถวที่ทำด้วยรุ่นเก่าจะถูกทำใหม่เองตอนเริ่มระบบ

## ข้อความจาก OCR ไม่ใช่ความจริงที่ยืนยันแล้ว

`textSource` แยกที่มาของข้อความออกเป็นสองแบบ:

| ค่า | ความหมาย |
|---|---|
| `NATIVE_TEXT` | สกัดจากข้อความที่ฝังอยู่ในไฟล์จริง เชื่อถือได้ |
| `OCR` | เครื่องอ่านจากภาพ **เป็นการคาดเดา อาจไม่ถูกต้องทั้งหมด** |

ผลที่ตามมาทั่วทั้งระบบ:

- ผลการค้นหาที่มาจาก OCR มีป้าย `OCR` กำกับ
- หน้ารายละเอียดแสดงคำเตือน "ข้อความจาก OCR อาจไม่ถูกต้องทั้งหมด" **เฉพาะ**เมื่อข้อความมาจาก OCR
  (การเตือนกับทุกอย่างเท่ากับไม่ได้เตือนอะไรเลย)
- การจัดลำดับให้ข้อความจากไฟล์จริงมาก่อนข้อความจาก OCR เสมอ
  ผลที่อ่านผิดจึงไม่ขึ้นก่อนชื่อไฟล์ที่ผู้ใช้ตั้งเอง

ค่าความมั่นใจที่เครื่องรายงานถูกเก็บไว้เป็น**ข้อมูลวินิจฉัย**เท่านั้น
**ห้ามใช้ตัดสินสิทธิ์** และไม่ถูกนำเสนอเป็นการรับประกันความถูกต้อง - หน้าจอเรียกมันว่า
"ความมั่นใจของระบบ" ไม่ใช่ "ความแม่นยำ"

### ความแม่นยำที่วัดได้จริง

จากการทดสอบบนเครื่องนี้:

- **ภาษาอังกฤษ**: อ่านถูกต้อง
- **ภาษาไทยบน PNG**: อ่านถูกต้อง (ผ่านการปรับรูปแบบแล้วตรงกับที่พิมพ์ทุกตัวอักษร)
- **ภาษาไทยบน JPEG ที่ถูกบีบอัด**: อ่านผิดบางตัวอักษร - พบกรณี `ก` ถูกอ่านเป็น `ค`
  ทำให้ค้นคำว่า `กำกับภาษี` ไม่เจอ แต่ค้น `ภาษี` และ `เลขที่` เจอตามปกติ

นี่คือธรรมชาติของ OCR ไม่ใช่ข้อบกพร่องที่แก้ได้ด้วยโค้ด และเป็นเหตุผลที่ระบบไม่นำเสนอ
ผลลัพธ์ราวกับเป็นความจริงที่ยืนยันแล้ว

## ความถูกต้องตามเวอร์ชัน

OCR ผูกกับ `ResourceVersion` หนึ่งเวอร์ชันเสมอ

ถ้า v1 ถูก OCR แล้ว v2 กลายเป็นเวอร์ชันปัจจุบัน การค้นหาปกติจะใช้ v2 เท่านั้น
ข้อความ OCR ของ v1 ยังอยู่เพื่อการตรวจสอบ แต่ไม่มีทางถูกคืนเป็นผลลัพธ์ปัจจุบัน

## สิทธิ์

| ใคร | ทำอะไรได้ |
|---|---|
| ผู้ที่มีสิทธิ์**แก้ไข**ไฟล์ | สั่ง OCR ไฟล์นั้นได้ |
| ผู้ที่เปิดดูได้อย่างเดียว | สั่งไม่ได้ |
| ผู้ดูแลระบบ | สั่งทีละหลายไฟล์ได้ |
| **ลูกค้า (EXTERNAL)** | **สั่ง OCR ไม่ได้เลยในเฟสนี้** |

OCR กิน CPU ของเครื่องทั้งเครื่อง จึงไม่ควรเป็นสิ่งที่ใครก็ตามที่เห็นไฟล์สั่งได้ตามใจ

OCR **ไม่ให้สิทธิ์เพิ่ม** - ผู้ใช้สั่งได้เฉพาะไฟล์ที่ตัวเองจัดการได้อยู่แล้ว
และไม่มีผลต่อสิทธิ์ในไดร์ฟของระบบแต่อย่างใด

ลูกค้าได้ประโยชน์จากผลของ OCR โดยอัตโนมัติผ่านการค้นหาที่ปลอดภัยตามสิทธิ์เดิม
เมื่อเจ้าหน้าที่ประมวลผลเอกสารในโฟลเดอร์ที่แชร์ให้แล้ว

## รหัสความล้มเหลว

| รหัส | ความหมาย | ลองใหม่ได้ |
|---|---|---|
| `OCR_NOT_CONFIGURED` | ยังไม่ได้ตั้งค่าเครื่องมือ | ไม่ |
| `OCR_UNSUPPORTED` | ไฟล์ชนิดนี้ไม่รองรับ | ไม่ |
| `OCR_IMAGE_TOO_LARGE` | ภาพใหญ่เกินกำหนด | ไม่ |
| `OCR_PAGE_LIMIT_EXCEEDED` | หน้ามากเกินกำหนด | ไม่ |
| `OCR_RENDER_FAILED` | ดึงภาพจากเอกสารไม่ได้ | ไม่ |
| `OCR_TIMEOUT` | ใช้เวลานานเกินกำหนด | ใช่ |
| `OCR_ENGINE_FAILED` | เครื่องมือทำงานไม่สำเร็จ | ใช่ |
| `OCR_NO_TEXT_FOUND` | ทำงานสำเร็จแต่ไม่พบข้อความ | (ไม่ใช่ความล้มเหลว) |

`OCR_NO_TEXT_FOUND` จบที่สถานะ `NO_TEXT` **ไม่ใช่ `FAILED`** เพราะเครื่องมือทำงานได้ปกติ
เพียงแต่เอกสารไม่มีตัวอักษร - เป็นข้อเท็จจริงเกี่ยวกับเอกสาร ไม่ใช่ข้อผิดพลาด

**ไม่มีบรรทัดคำสั่งดิบใดปรากฏใน API หรือ log** มีแต่รหัสสั้น ๆ เหล่านี้

## สิ่งที่เฟสนี้ไม่ได้ทำ

- การค้นหาเชิงความหมายหรือ vector search
- การแก้ไขข้อความที่ OCR อ่านได้ด้วยมือ
- การสร้างไฟล์ผลลัพธ์ให้ดาวน์โหลด (`.txt` / `.docx`)
- การยกเลิกงานที่กำลังทำงานอยู่ (ยกเลิกได้เฉพาะงานที่ยังรออยู่ในคิว)
- OCR อัตโนมัติทุกไฟล์

## F14 - ข้อความที่คนตรวจแก้แล้ว

ผลของ OCR แก้ได้ด้วยมือ และข้อความที่แก้แล้วจะถูกใช้แทนผลดิบในการค้นหา

ที่มาของข้อความจึงมีสามแบบ ไม่ใช่สองแบบอีกต่อไป

| ที่มา | ความน่าเชื่อถือ |
|---|---|
| `NATIVE_TEXT` | ข้อความที่ฝังอยู่ในไฟล์จริง |
| `OCR` | เครื่องเดาจากภาพ อาจผิด |
| `HUMAN_CORRECTED` | คนอ่านด้วยตาแล้วยืนยัน |

**ผลดิบของ OCR ไม่หายไป** เก็บไว้ใน `rawOcrText` ถาวร กดปุ่ม *ใช้ผล OCR เดิม*
เมื่อไรก็กลับไปได้ และยังใช้ตอบได้ว่าเครื่องอ่านผิดตรงไหน

**สั่ง OCR ใหม่ไม่ลบงานที่คนแก้ไว้** ผลรอบใหม่ไปนั่งรออยู่ใน `rawOcrText` ให้เทียบ
ส่วนข้อความที่ใช้ค้นหายังเป็นฉบับที่คนยืนยัน

**ไฟล์ต้นฉบับไม่ถูกแตะแม้แต่ไบต์เดียว** การตรวจแก้แก้เฉพาะดัชนีค้นหา
