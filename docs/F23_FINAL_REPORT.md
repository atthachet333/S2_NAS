# F23 final report — Storage Scale / Object Storage

วันที่ตรวจ: 14 กันยายน 2026
Baseline: `e37524a` (F22 smart filing)
Release state: **implemented, uncommitted, ค่าเริ่มต้นยังเป็น LOCAL**

> **สถานะที่ต้องอ่านก่อนอย่างอื่น:** ปลายทาง S3 จริงยัง **ไม่ถูกทดสอบ** ไม่มีการเชื่อมต่อ
> ไปยัง R2, AWS หรือ MinIO ตัวจริงเลยตลอดทั้ง F23 หลักฐานทั้งหมดของฝั่ง S3 มาจากชั้น
> ขนส่งจำลองที่สวมแทน `S3Client` โดยโค้ดผู้ให้บริการตัวจริงยังเป็นสิ่งที่ถูกทดสอบ
> รายละเอียดและขอบเขตของความเสี่ยงอยู่ในหัวข้อ 9

## 1. สิ่งที่ F23 เปลี่ยน

1. **ไบต์ของเอกสารเดินผ่านผู้ให้บริการ ไม่ใช่ผ่าน `node:fs` โดยตรงอีกต่อไป** `LocalStorageProvider` เป็นที่เดียวที่ยังรู้จักไฟล์ระบบสำหรับไบต์ของเอกสาร ตรรกะเดิมถูกยกมาคำต่อคำ ไม่ได้เขียนใหม่
2. **ทุกแถวถือชนิดพื้นที่จัดเก็บของตัวเอง** `Resource.storageProvider` และ `ResourceVersion.storageProvider` เป็นตัวชี้ขาดของการอ่าน ไม่ใช่ค่าตั้งปัจจุบันของระบบ
3. **ไม่มีการถอยไปหาผู้ให้บริการอื่นเด็ดขาด** แถวที่บอกว่าอยู่บน S3 แล้วอ่านไม่เจอ คือความไม่สอดคล้องที่ต้องถูกรายงาน ไม่ใช่สิ่งที่ควรกลบด้วยการลองหาที่อื่น
4. **การสลับ `S2_NAS_STORAGE_PROVIDER` เปลี่ยนเฉพาะปลายทางของการเขียนใหม่** ของเดิมยังถูกอ่านจากที่เดิม สภาพผสม LOCAL/S3 เป็นสภาพปกติที่รองรับ ไม่ใช่ช่วงเปลี่ยนผ่านที่ต้องรีบให้จบ
5. **ไม่มี `move()` ในสัญญา** การย้าย เปลี่ยนชื่อ กู้คืน และโอนเจ้าของ เป็นการแก้ข้อมูลกำกับล้วน ๆ การมี `move()` จะชวนให้ผู้เรียกย้ายไบต์ในงานที่ต้องไม่แตะไบต์
6. **`localPathFor` เป็นทางออกฉุกเฉินเพื่อความเข้ากันได้ ไม่ใช่ API** ใช้ได้เฉพาะ OCR การสกัดข้อความ และตัวช่วยโครงสร้างพื้นฐานที่รู้เรื่องผู้ให้บริการ ชั้นธุรกิจใช้ `withLocalMaterialization` แทน ซึ่งลบไฟล์ชั่วคราวใน `finally` เสมอ

## 4. การสำรองและกู้คืนที่ไม่ผูกกับผู้ให้บริการ

11. **`PORTABLE_FULL`** อ่านไบต์จากผู้ให้บริการที่แต่ละแถวระบุ ชุดสำรองเดียวจึงกู้กลับไปยังผู้ให้บริการใดก็ได้
12. **manifest v2** บันทึก `resourceVersionId` และ `originalProvider` โดย `originalProvider` เป็นข้อมูลประกอบเท่านั้น
13. **ปลายทางการกู้คืนมาจากคำสั่ง ไม่เคยอนุมานจาก manifest** ทดสอบครบทั้งหกทิศทางข้ามผู้ให้บริการ
14. **ด่านกันชั่วคราวถูกถอดออกใน F23-F พร้อมหลักฐาน** ไม่ใช่ถอดเพราะมันขวางทาง

**การสำรองจริงวันนี้:** 1,765 ไฟล์ · ฐานข้อมูล 83.4 MB · รวม 1.3 GB
**การซ้อมกู้คืนจริงวันนี้: ผ่าน** — 1,925 ทรัพยากร · 1,765 เวอร์ชัน · หาย 0 · กำพร้า 0 · checksum ล้มเหลว 0

การซ้อมนี้อ่านและตรวจ checksum ของวัตถุทุกชิ้นในคลัง หลังการเปลี่ยนแปลงของ F23-G ทั้งหมดแล้ว

## 5. ข้อบกพร่องที่พบและแก้ใน F23-G

15. **`classifyS3Error` จำแนก `ECONNREFUSED` เป็น `UNKNOWN`** เพราะ `??` ลัดวงจรที่ `err.name === 'Error'` ทำให้ปลายทางที่ติดต่อไม่ได้ถูกรายงานเป็นความผิดพลาดทั่วไป แก้ให้ตรวจทุกช่องที่เป็นไปได้ (`name`, `Code`, `code`, `cause.code`, `cause.name`) เพิ่มการทดสอบถดถอย 9 รายการด้วยรูปร่างข้อผิดพลาดของซ็อกเก็ตจริง
16. **เศษ `restore-stage` ไม่เคยถูกตรวจพบ** เพราะการสแกนทำงานเฉพาะเมื่อมีแถวอ้างถึง S3 อยู่แล้ว ซึ่งเป็นเงื่อนไขที่ผิด เพราะเศษจากการกู้คืนที่ถูกขัดจังหวะมีได้โดยไม่มีแถวใดอ้างถึง S3 เลย แก้ให้ตรวจสุขภาพ S3 อย่างอิสระ
17. **ไม่มีการมองเห็นปฏิบัติการพื้นที่จัดเก็บ** มีแต่การบันทึกตอนล้มเหลว เพิ่ม `withStorageTelemetry` ห่อที่ทะเบียน ทำให้ผู้ให้บริการทุกตัว **รวมถึงตัวที่เพิ่มในอนาคต** ถูกมองเห็นเท่ากันโดยอัตโนมัติ

## 6. การมองเห็น

บันทึกทุกปฏิบัติการ: ชนิดผู้ให้บริการ · ชื่อปฏิบัติการ · เวลาที่ใช้ · จำนวนไบต์ · สำเร็จหรือล้มเหลว

**ไม่บันทึก** คีย์วัตถุ เส้นทางบนดิสก์ ชื่อถัง ปลายทาง กุญแจ หรือเนื้อหาเอกสาร — คีย์มีรหัสทรัพยากรอยู่ข้างใน และปูมมักไหลไปยังระบบที่มีคนเข้าถึงได้กว้างกว่าตัวระบบเอง มีการทดสอบบังคับข้อนี้โดยตรง

**ข้อจำกัดที่บันทึกไว้:** ปฏิบัติการที่คืนสตรีม เวลาที่วัดคือเวลาจนสตรีมพร้อม ไม่ใช่เวลาถ่ายโอนจบ

## 7. การทดสอบผ่านเบราว์เซอร์

ทำกับข้อมูลทดสอบที่สร้างขึ้นเฉพาะกิจ บนเซิร์ฟเวอร์ที่ผู้ใช้รันอยู่ (หน้าบ้าน :8888 หลังบ้าน :8889)

| ขั้นตอน | ผล |
|---|---|
| เข้าระบบในฐานะผู้ดูแล | ผ่าน |
| อัปโหลด | ผ่าน |
| ดาวน์โหลด | ผ่าน — `200 OK` |
| อัปโหลดเวอร์ชันใหม่ | ผ่าน — `storageKey` เปลี่ยน `currentVersion: 2` checksum เปลี่ยน |
| ข้อมูลรั่วใน API | ผ่าน — คำตอบจริงที่เบราว์เซอร์ได้รับไม่มี `storageKey`, `storageProvider`, ชื่อถัง, เส้นทาง หรือ checksum |
| หน้าตรวจสุขภาพ | ผ่าน — `{"defaultProvider":"LOCAL","providers":{"LOCAL":"READY","S3":"NOT_CONFIGURED"}}` |
| ย้ายโฟลเดอร์ | **ไม่ได้ทดสอบผ่านหน้าจอจริง** (ดูด้านล่าง) |
| ทุกขั้นตอนฝั่ง S3 | **ไม่ได้ทดสอบ** — ไม่มีปลายทางจริง |

**การย้าย:** ปุ่มย้ายอยู่ในชั้นซ้อนที่เครื่องมือควบคุมเบราว์เซอร์เข้าไม่ถึงอย่างเสถียร จึงเรียก `moveResource` ซึ่งเป็นบริการเดียวกับที่หน้าจอเรียกแทน แล้วพิสูจน์ที่ฐานข้อมูลว่า `parentId` เปลี่ยน ส่วน `storageKey` `storageProvider` `checksum` และคีย์ของทุกเวอร์ชันย้อนหลัง **ไม่เปลี่ยนแม้แต่ค่าเดียว** ซึ่งพิสูจน์ว่าการย้ายเป็นการแก้ข้อมูลกำกับล้วน ๆ แต่ **ไม่ได้พิสูจน์ว่าปุ่มบนหน้าจอเรียกเส้นทางนั้น** จึงรายงานว่าไม่ได้ทดสอบผ่านหน้าจอจริง ตามหลักที่ตกลงกันว่าให้รายงานตามจริงแทนการอ้างว่าผ่าน

## 8. ความปลอดภัยและความสะอาดของระบบ

18. **ไม่มีกุญแจอยู่ในที่เก็บโค้ดหรือใน `.env`** `.env` มีเวลาแก้ไขล่าสุด 9 กันยายน ซึ่งก่อนงานรอบนี้ทั้งหมด และไม่มีคีย์ `S2_NAS_S3_*` อยู่เลย
19. **ไม่มีกุญแจค้างในสภาพแวดล้อมของกระบวนการ**
20. **ไม่มีการหมุนกุญแจใด ๆ**
21. เปลี่ยนกุญแจปลอมในบททดสอบทางลบจาก `AKIA…` เป็น `not-a-real-key-for-qa-only` เพราะคำนำหน้าเดิมทำให้เครื่องสแกนความลับแจ้งเตือนผิด โดยความหมายของการทดสอบไม่เปลี่ยน
22. **ไม่เคยตั้ง ACL และไม่เคยออก presigned URL** การอนุญาตไม่ถูกโอนไปให้ที่เก็บวัตถุ ดาวน์โหลดยังผ่านสตรีมที่ตรวจสิทธิ์แล้วเสมอ
23. **ไม่ใช้ ETag เป็น checksum** เพราะมันไม่ใช่แฮชของเนื้อหาสำหรับวัตถุแบบหลายส่วน

**สภาพคลังหลังงานเสร็จ:** เวอร์ชันบน S3 = 0 · ทรัพยากรบน S3 = 0 · ค่าเริ่มต้น LOCAL · `S3: NOT_CONFIGURED`

**การเก็บกวาดที่ทำ:** ลบวัตถุกำพร้าที่ชุดทดสอบวันนี้สร้างขึ้น 88 รายการ (ตรวจการอ้างอิงซ้ำทีละไฟล์ก่อนลบ) · ลบไฟล์พักอัปโหลดค้าง 258 รายการ · ลบข้อมูลทดสอบ F23-G ทั้งหมด · เศษ `materialize-*` = 0 · เศษ `restore-stage` = 0

**ของเดิม 6,309 รายการไม่ถูกแตะ** ยืนยันยอดคงเดิมเป๊ะทั้งก่อนและหลังการเก็บกวาด

## 9. ความเสี่ยงที่ยังเหลืออยู่ และข้อบกพร่องที่เปิดค้าง

**ความเสี่ยงที่ยอมรับไว้อย่างชัดแจ้ง — ยังไม่เคยต่อกับปลายทาง S3 จริง**

สิ่งที่พิสูจน์แล้วคือ โค้ดผู้ให้บริการตัวจริงประกอบคำสั่งถูกต้อง จัดการสตรีม ช่วงไบต์ การพัก การยืนยัน และการจำแนกความล้มเหลวได้ถูกต้อง โดยสวมชั้นขนส่งจำลองแทน `S3Client`

สิ่งที่ **ยังไม่ได้พิสูจน์** และจะรู้ได้ก็ต่อเมื่อต่อกับปลายทางจริงเท่านั้น:

- พฤติกรรมการลองใหม่และการหมดเวลาจริงของ SDK บนเครือข่ายจริง
- ความเข้ากันได้ของผู้ให้บริการแต่ละเจ้า (R2, AWS, MinIO มีพฤติกรรมต่างกันในรายละเอียด)
- ผลลัพธ์ของการลบหลายวัตถุที่สำเร็จบางส่วน
- ความเร็วและพฤติกรรมหน่วยความจำจริงกับไฟล์ขนาดใหญ่ข้ามเครือข่าย
- รูปร่างข้อผิดพลาดจริงที่ต่างจากที่จำลองไว้

`npm run qa:s3-smoke` ถูกเขียนไว้พร้อมใช้ (17 ขั้นตอน ใช้ prefix สุ่มต่อรอบ และปฏิเสธที่จะทำงานถ้าไม่มีกุญแจ) เมื่อมีปลายทางจริงให้รันคำสั่งเดียวนี้ก่อนเปิดใช้ S3 ในงานจริง

**ข้อสังเกตที่มีมาก่อน F23 ไม่ได้แก้ในรอบนี้:**

- บัญชีทดสอบค้างในฐานข้อมูล 9 บัญชี จากชุดทดสอบ F14/F16 เมื่อ 8–11 กันยายน (หนึ่งบัญชีเป็นเจ้าของทรัพยากร 15 รายการ) งานรอบนี้ไม่ได้สร้างเพิ่มแม้แต่บัญชีเดียว และไม่ได้ลบของเดิมเพราะอยู่นอกขอบเขต F23
- ไม่มีตัวกวาดไฟล์พักอัปโหลดที่ถูกทิ้งค้าง ถ้ากระบวนการดับกลางคัน ไบต์ที่พักไว้จะค้างอยู่จนกว่าจะมีคนลบ เป็นสภาพที่มีมาก่อน F23 และอยู่นอกขอบเขตของงานนี้
- วัตถุกำพร้าในคลังจริง 6,309 รายการ ยังคงอยู่ตามที่สั่งไว้

## 10. เหตุการณ์ที่ต้องบันทึกไว้

ระหว่าง F23-E การรัน `migrateStorage({from:'LOCAL',to:'S3',limit:2})` โดยไม่ระบุขอบเขต ได้เลือกเวอร์ชัน LOCAL ที่เก่าที่สุดจากทั้งฐานข้อมูล ทำให้แถวของผู้ใช้จริง 6 แถวถูกย้ายไปชี้ที่ S3 พบขณะกำลังตรวจสอบยอดวัตถุกำพร้าที่ดูผิดปกติ

**ไม่มีข้อมูลสูญหาย** เพราะการย้ายไม่เคยลบต้นทาง ทั้ง 6 แถวถูกเปลี่ยนกลับเป็น LOCAL หลังตรวจไบต์บนดิสก์เทียบกับ SHA-256 ที่บันทึกไว้แล้ว และได้เพิ่ม `resourceIds` เข้าไปในทั้ง API และชุดทดสอบทั้งหมด เพื่อให้การรันที่ไม่ระบุขอบเขตไม่ใช่พฤติกรรมโดยปริยายอีกต่อไป

## 11. สรุป

F23 **เสร็จสมบูรณ์ยกเว้นการตรวจกับปลายทางจริง** ด่านบังคับทุกด่านที่ไม่ต้องใช้ปลายทางจริงผ่านหมด ข้อบกพร่องที่เปิดค้างภายในขอบเขตที่ทดสอบได้: **0**

**ไม่ประกาศว่า F23 COMPLETE / 0 OPEN DEFECTS แบบไม่มีเงื่อนไข** เพราะข้อกำหนดระบุว่าห้ามประกาศบนหลักฐานจาก S3 จำลองเพียงอย่างเดียว เว้นแต่จะยอมรับการไม่ได้ตรวจปลายทางจริงเป็นความเสี่ยงที่เหลืออยู่อย่างชัดแจ้ง ซึ่งเป็นทางที่เลือกไว้ และระบุไว้ในหัวข้อ 9
