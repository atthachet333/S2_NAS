# ประวัติการอัปโหลดของลูกค้า (Client upload history)

เฟส F12 เพิ่มหน้า `/portal/uploads` ให้ลูกค้าตอบสามคำถามได้ด้วยตัวเอง:

**ฉันอัปโหลดอะไรไปแล้ว · เมื่อไร · ไว้ที่ไหน**

## หลักการเดียวที่สำคัญที่สุด

**ประวัติไม่ใช่ช่องทางเข้าถึงที่สอง**

- **รายการ** ถูกตัดสินจาก "ใครเป็นผู้อัปโหลด" ซึ่งเป็นข้อเท็จจริงที่เปลี่ยนไม่ได้
- **การเปิดดูและดาวน์โหลด** ถูกตัดสินจาก "สิทธิ์ที่มีอยู่ตอนนี้" เสมอ

ผลคือไฟล์ที่เคยส่งไปแล้วถูกเจ้าหน้าที่ย้ายออกนอกขอบเขต หรือถูกลบ หรือสิทธิ์หมดอายุ
จะยังปรากฏว่าเคยส่ง แต่เปิดไม่ได้อีก

**การเคยอัปโหลดไฟล์หนึ่งไม่ได้ทำให้ได้สิทธิ์ถาวรกับไฟล์นั้น**

## ขอบเขตของข้อมูล

```
createdById  = ผู้ใช้ที่กำลังดูอยู่
sourceType   = EXTERNAL_UPLOAD
```

เงื่อนไขผูกกับรหัสผู้ใช้ในคำสั่งฐานข้อมูลโดยตรง **ลูกค้ารายหนึ่งจึงไม่มีทางเห็นของอีกราย**
และไฟล์ที่เจ้าหน้าที่อัปโหลดเองก็ไม่ปรากฏในประวัติของลูกค้า

## สถานะของแต่ละรายการ

| สถานะ | ข้อความ | ความหมาย |
|---|---|---|
| `AVAILABLE` | พร้อมใช้งาน | ยังอยู่ในขอบเขตที่เข้าถึงได้ |
| `MANAGED_BY_STAFF` | เจ้าหน้าที่รับเรื่องแล้ว | ไฟล์ยังอยู่ แต่ถูกย้ายออกนอกขอบเขตของลูกค้า |
| `UNAVAILABLE` | ไฟล์นี้ไม่สามารถเข้าถึงได้แล้ว | ถูกย้ายไปถังขยะหรือลบ |

`MANAGED_BY_STAFF` **ไม่ใช้สีเตือน** โดยตั้งใจ - ลูกค้าที่ส่งเอกสารสำเร็จแล้วเห็นสีแดง
จะเข้าใจว่าส่งไม่สำเร็จ ทั้งที่สำเร็จแล้ว

## ความปลอดภัยของปลายทาง

เส้นทางปลายทางแสดง**เฉพาะเมื่อยังเข้าถึงได้** และถูกตัดให้เริ่มที่รากที่ได้รับสิทธิ์เสมอ

เมื่อไฟล์ถูกย้ายออกนอกขอบเขต **เราไม่บอกว่ามันถูกย้ายไปที่ไหน** - `destination` เป็น `null`
การบอกตำแหน่งใหม่คือการเปิดเผยโครงสร้างภายในขององค์กรให้คนนอก

มีชุดทดสอบยืนยันว่าชื่อโฟลเดอร์ภายในไม่หลุดออกไปกับผลลัพธ์แม้แต่ตัวอักษรเดียว

## ถังขยะ

ไฟล์ที่ถูกลบยังอยู่ในประวัติว่า**เคยส่ง** แต่:

- ไม่มีปุ่มเปิดดูและไม่มีปุ่มดาวน์โหลด
- เรียก API ตรง ๆ ด้วยรหัสที่รู้จากประวัติของตัวเองก็ได้ `404` เหมือนเดิม
- **ลูกค้าไม่มีทางเข้าถังขยะ** และไม่มีทางกู้คืน

## สิทธิ์ดาวน์โหลด

ปุ่มดาวน์โหลดปรากฏก็ต่อเมื่อ `allowDownload` ของสิทธิ์ปัจจุบันอนุญาต

โฟลเดอร์รับเอกสารที่ให้สิทธิ์ "อัปโหลดได้" แต่ไม่ให้ดาวน์โหลด เป็นรูปแบบที่ใช้จริง -
ลูกค้าส่งเอกสารเข้ามาได้ แต่ดึงกลับไม่ได้ **การอัปโหลดเองไม่ได้แปลว่าดาวน์โหลดกลับได้**

## เส้นทาง API

```
GET /api/portal/uploads?q=&extension=&from=&to=&limit=&cursor=
GET /api/portal/uploads/types
```

- เรียงใหม่สุดก่อน - ลูกค้ามองหาสิ่งที่เพิ่งส่งไปเป็นอันดับแรกเสมอ
- แบ่งหน้าด้วย cursor สูงสุด 100 รายการต่อหน้า
- ตัวกรอง: ชื่อไฟล์ · ประเภทไฟล์ · ช่วงวันที่
- `types` คืนเฉพาะนามสกุลที่ลูกค้ารายนี้เคยส่งมาจริง ไม่ใช่รายการทั้งระบบ

การไล่หาบรรพบุรุษทำเป็นชั้น ๆ หนึ่งคำสั่งต่อหนึ่งชั้น **ไม่ใช่หนึ่งคำสั่งต่อหนึ่งไฟล์**
ซึ่งจะกลายเป็น N+1 ทันทีที่ประวัติยาวขึ้น

## การเชื่อมกับบันทึกร่องรอย

ทุกการอัปโหลดของลูกค้ามีบันทึก `EXTERNAL_FILE_UPLOADED` อยู่แล้วตั้งแต่ F10

ประวัติที่ลูกค้าเห็นสร้างจาก**ทรัพยากรจริง** ไม่ใช่จากตารางบันทึก
เพราะบันทึกมี metadata ภายในที่ไม่ควรส่งออกไปฝั่งลูกค้า และสถานะปัจจุบันของไฟล์
ต้องมาจากไฟล์เอง ไม่ใช่จากเหตุการณ์ในอดีต

## มุมมองของเจ้าหน้าที่

ฝั่งภายในกรองไฟล์ที่ลูกค้าส่งเข้ามาได้ด้วยตัวกรองที่มีอยู่แล้ว: `sourceType = EXTERNAL_UPLOAD`
ซึ่งแสดงเป็น "ลูกค้าอัปโหลด" ในหน้าค้นหาและในรายการไฟล์

ไม่มีการสร้างหน้าจัดการลูกค้าเพิ่มในเฟสนี้ - ดู [CLIENT_PORTAL.md](CLIENT_PORTAL.md) สำหรับหน้า `/admin/clients`

## สิ่งที่เฟสนี้ไม่ได้ทำ

- ลูกค้าลบหรือแก้ไขไฟล์ที่ตัวเองส่งไปแล้ว (เจตนาเดิมตั้งแต่ F10)
- การแจ้งเตือนเมื่อเจ้าหน้าที่รับเรื่อง
- การตอบกลับหรือแสดงความคิดเห็นบนเอกสาร
