# การเข้าถึงของแขก

สิ่งที่เกิดขึ้นเมื่อคนนอกองค์กรเปิดลิงก์ที่เราส่งให้

## แขกไม่ใช่ผู้ใช้

การเปิดลิงก์แชร์ **ไม่สร้างอะไรเลย** ในระบบตัวตน:

- ไม่มีแถวใน `User`
- ไม่มี `UserIdentity`
- ไม่มี session ของพื้นที่ลูกค้า
- ไม่มี access token ภายใน

ผู้ถือโทเคนเป็นตัวตนของตัวเอง (`GUEST_SHARE`) ที่มีสิทธิ์เท่ากับสิ่งที่เขียนไว้
บนแถวลิงก์นั้นแถวเดียว และไม่มีทางกลายเป็นผู้ใช้ได้

**ผู้ใช้ภายนอกที่ล็อกอินอยู่แล้วเปิดลิงก์แขก** จะถูกปฏิบัติในฐานะแขกของลิงก์นั้น
ไม่ใช่การขยายสิทธิ์ในพื้นที่ลูกค้าของเขา - เส้นทาง `/api/public/shares/*`
ไม่อ่าน session ของใครเลย

## หน้าจอของแขก

เปลือกหน้าจอเป็นของตัวเองทั้งชุด **ไม่ใช้ร่วมกับพื้นที่ทำงานภายในหรือพื้นที่ลูกค้า**

ไม่มี: เมนู · ไดร์ฟ · ถังขยะ · เมนูผู้ดูแล · รูปผู้ใช้ · ลิงก์ไปหน้าอื่นในระบบ

มีแค่ชื่อ **S2 NAS** ซึ่งเป็นข้อความ ไม่ใช่ปุ่ม

เหตุผลที่ไม่ใช้เปลือกร่วมแล้วซ่อนเมนูทีละอัน: วันที่มีคนเพิ่มเมนูใหม่แล้วลืมซ่อน
เมนูนั้นจะโผล่ให้คนนอกเห็น หน้านี้จึงไม่มีอะไรให้ลืมซ่อนตั้งแต่ต้น

### หน้าไฟล์

```
S2 NAS

เอกสารที่แชร์กับคุณ
สัญญาจ้าง-2569.pdf
PDF • 2.4 MB

[ดูเอกสาร]  [ดาวน์โหลด]

ลิงก์หมดอายุ: 14 กันยายน 2569
```

ปุ่มดาวน์โหลด **ไม่ปรากฏเลย** เมื่อลิงก์ไม่อนุญาต - ไม่ใช่ปุ่มที่กดแล้วถูกปฏิเสธ

### หน้าโฟลเดอร์

แสดงชื่อโฟลเดอร์ที่แชร์ รายการลูก และเส้นทางนำทางที่**เริ่มต้นที่โฟลเดอร์ที่แชร์**

## สิ่งที่แขกไม่เห็น

```
ผู้ดูแลหลัก · อีเมล · แท็ก · หมายเหตุ · ประเภทเอกสาร
นโยบายการเก็บรักษา · สถานะคลัง · Legal Hold
โฟลเดอร์แม่ที่อยู่เหนือราก · ไดร์ฟ
storageKey · checksum · เส้นทางไฟล์จริง · หมายเลขเวอร์ชัน · ผู้สร้าง
```

ชื่อคนและโครงสร้างโฟลเดอร์ขององค์กรเป็นข้อมูลทางธุรกิจ
คนที่ได้รับเอกสารหนึ่งฉบับไม่ควรได้แผนผังองค์กรแถมไปด้วย

## ขอบเขตของโฟลเดอร์

เมื่อแชร์โฟลเดอร์ แขกเดินได้เฉพาะในกิ่งนั้น **ไม่มีทางขึ้นไปเหนือราก**

การตรวจอยู่ที่เซิร์ฟเวอร์ทั้งหมด: ระบบไต่จาก id ที่ขอมาขึ้นไปหาแม่ทีละชั้น
จนกว่าจะเจอรากที่ลิงก์นี้แชร์ไว้ ถ้าไม่เจอ คำตอบคือ "ไม่พบ"

แขกแก้ id ใน URL ได้ตามใจ - id ของเอกสารในโฟลเดอร์อื่น หรือของโฟลเดอร์แม่
ที่อยู่เหนือราก - ผลลัพธ์เหมือนกันหมด

ชั้นใดชั้นหนึ่งในสายที่ถูกลบหรือเก็บเข้าคลัง ทำให้ทั้งกิ่งหายไปจากสายตาแขก
ถ้าตรวจเฉพาะตัวเอกสาร การเก็บโฟลเดอร์แม่เข้าคลังจะไม่มีผลกับลูก

## รหัสผ่าน

เมื่อลิงก์มีรหัสผ่าน หน้าแรกที่แขกเห็นบอกเพียงว่า **"เอกสารนี้ต้องใช้รหัสผ่าน"**
ยังไม่บอกแม้แต่ชื่อไฟล์ - ชื่ออย่าง "สัญญาเลิกจ้าง_สมชาย.pdf" บอกเรื่องราวไปครึ่งหนึ่งแล้ว

รหัสถูกต้อง → ระบบออก **ใบผ่านชั่วคราว** อายุ 2 ชั่วโมง ผูกกับลิงก์นั้นลิงก์เดียว
เก็บไว้ใน `sessionStorage` ของแท็บนั้น (ปิดแท็บแล้วหาย)

ใบผ่านตอบได้เพียงคำถามเดียว: "คนนี้เคยพิมพ์รหัสผ่านถูกหรือไม่"
**มันไม่ข้ามการตรวจสถานะลิงก์** ทุกคำขอยังอ่านแถวในฐานข้อมูลใหม่เสมอ
การยกเลิกจึงมีผลทันทีแม้ใบผ่านจะยังไม่หมดอายุ

ใบผ่านของลิงก์ A ใช้กับลิงก์ B ไม่ได้ และใช้กับเส้นทางภายในไม่ได้เลย
(ผู้รับ/audience ของโทเคนต่างกันคนละตัว จึงถูกปฏิเสธที่ชั้นลายเซ็น)

## ข้อความเมื่อใช้ไม่ได้

โทเคนผิด · ลิงก์ถูกยกเลิก · ลิงก์หมดอายุ · ใช้ครบจำนวน · เอกสารถูกลบ ·
เอกสารอยู่ในคลัง — ทั้งหมดได้ข้อความเดียวกัน:

> **ลิงก์นี้ไม่สามารถใช้งานได้แล้ว**
> กรุณาติดต่อผู้ที่ส่งลิงก์นี้ให้คุณเพื่อขอลิงก์ใหม่

ถ้าตอบต่างกัน ผู้ที่สุ่มโทเคนไปเรื่อย ๆ จะแยกออกว่า "โทเคนนี้เคยมีอยู่จริงแต่หมดอายุ"
กับ "ไม่เคยมี" ซึ่งช่วยเขาได้จริงในการค้นหาต่อ ส่วนผู้รับตัวจริงต้องติดต่อผู้ส่งอยู่ดี

ข้อความที่เจาะจงกว่ามีเฉพาะกรณีที่บอกแล้วไม่เสียหาย เช่น "ลิงก์นี้ไม่อนุญาตให้ดาวน์โหลด"
ซึ่งเจ้าของลิงก์ตั้งใจให้เป็นแบบนั้นอยู่แล้ว

## การนับ

**การเปิด (view)** นับหนึ่งครั้งเมื่อหน้าของแขกเปิดสำเร็จ ไม่ใช่ทุกคำขอ

การดู PDF หนึ่งฉบับสร้างคำขอช่วงข้อมูลนับสิบครั้ง ถ้านับทุกครั้ง เพดาน "เปิดได้ 3 ครั้ง"
จะหมดตั้งแต่คนแรกยังเลื่อนไม่ถึงหน้าสอง และตัวเลขในรายงานจะไม่ตรงกับความจริงเลย

**การดาวน์โหลด** นับเมื่อได้รับอนุญาตและเริ่มส่งไฟล์จริง ครั้งที่ถูกปฏิเสธไม่นับ

เมื่อ `maxViews` ครบ → ลิงก์ใช้ไม่ได้ทั้งลิงก์
เมื่อ `maxDownloads` ครบ → ดาวน์โหลดไม่ได้ แต่ **ยังเปิดดูได้** ถ้าลิงก์อนุญาต

การจองโควตาดาวน์โหลดเป็น **อะตอมมิก** สองคำขอพร้อมกันในโควตาที่เหลือหนึ่งครั้ง
มีผู้ชนะได้คนเดียวเสมอ ดู [PUBLIC_SHARE_SECURITY.md](PUBLIC_SHARE_SECURITY.md)

## การบันทึก

ทุกการกระทำของแขกถูกบันทึกพร้อม IP และสรุปอุปกรณ์ โดย `userId` เป็น **null**
หน้าตรวจสอบจึงแสดงผู้ดำเนินการว่า "ระบบ" - ตัวตนที่แท้จริงคือ `shareLinkId` ใน metadata
ซึ่งเป็นสิ่งเดียวที่เรารู้จริงเกี่ยวกับเขา

**ไม่มีสคริปต์ติดตามและไม่มีการเก็บลายนิ้วมือเบราว์เซอร์** ทุกไฟล์ที่หน้านี้โหลด
มาจากเซิร์ฟเวอร์ของเราเอง ไม่มีบริการภายนอกที่ได้เห็น URL ที่มีโทเคนอยู่ข้างใน
