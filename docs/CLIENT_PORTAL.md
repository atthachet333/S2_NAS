# พื้นที่เอกสารสำหรับลูกค้า (Client Portal)

เฟส F10 เพิ่มบัญชีผู้ใช้งานภายนอกและพื้นที่ `/portal` ให้ลูกค้าเข้าถึงเฉพาะเอกสารที่บริษัทแชร์ให้เท่านั้น

## หลักการที่ทั้งเฟสนี้ยึด

1. **ชนิดบัญชีมีน้ำหนักเหนือบทบาทเสมอ**
   บัญชี `EXTERNAL` ที่เผลอได้รับบทบาทภายในกว้าง ๆ ก็ยังทำได้เท่าที่นโยบายภายนอกอนุญาต
   ด่าน `requireInternal` ปฏิเสธคำขอตั้งแต่ก่อนถึงตรรกะของโมดูลใด ๆ และ `capabilities()`
   ของฝั่งภายในคืนค่าปฏิเสธทั้งหมดให้บัญชีภายนอกเป็นชั้นป้องกันสุดท้าย

2. **ไม่มีสิทธิ์โดยปริยาย**
   ไม่มีอะไรที่ "เห็นได้เพราะเป็นขององค์กร" สำหรับลูกค้า
   เห็นได้เฉพาะสิ่งที่ถูกแชร์ให้โดยตรง และสิ่งที่อยู่ใต้โฟลเดอร์ที่ถูกแชร์ให้

3. **อ่านและเพิ่ม ไม่ลบและไม่แก้**
   ลูกค้าเปลี่ยนแปลงของเดิมไม่ได้เลย แม้แต่ไฟล์ที่ตัวเองอัปโหลดขึ้นมา
   การควบคุมเอกสารยังเป็นของบุคลากรภายในเสมอ

## ชนิดบัญชี

`UserType` เปลี่ยนจาก `HUMAN | SERVICE` เป็น `INTERNAL | EXTERNAL | SERVICE`

| ค่า | ความหมาย |
|---|---|
| `INTERNAL` | บุคลากรขององค์กร ใช้พื้นที่ทำงานภายในตามบทบาทและสิทธิ์ปกติ |
| `EXTERNAL` | ลูกค้า เห็นได้เฉพาะสิ่งที่ถูกแชร์ให้ ผ่าน `/portal` เท่านั้น |
| `SERVICE` | บัญชีตัวแทนของระบบเชื่อมต่อ ไม่ใช่มนุษย์ |

การเปลี่ยนชื่อ `HUMAN` → `INTERNAL` ทำเป็นสามขั้นใน migration เดียว (เปิดรับค่าใหม่ → ย้ายข้อมูล → ปิดค่าเดิม)
การสั่ง `MODIFY` ไปยังชุดค่าใหม่ทันทีจะทำให้ MariaDB แปลงค่าเดิมเป็นค่าว่างโดยไม่แจ้งเตือน

ฟิลด์ `organizationName` เก็บชื่อบริษัทของลูกค้า เป็นข้อมูลประกอบสำหรับหน้าจัดการเท่านั้น
ไม่ใช่ขอบเขตสิทธิ์ - ลูกค้าสองรายที่อยู่บริษัทเดียวกันยังเห็นเฉพาะสิ่งที่ถูกแชร์ให้ตัวเอง

## บทบาทในพื้นที่ลูกค้า

ใช้ `ResourceAccess` เดิม ไม่มีตารางสิทธิ์ชุดที่สอง

| ระดับที่มอบให้ | บทบาทในพื้นที่ลูกค้า | ทำได้ |
|---|---|---|
| `VIEWER` | ดูอย่างเดียว | เปิดดู · ดาวน์โหลดเมื่อ `allowDownload = true` |
| `EDITOR` | อัปโหลดได้ | ทุกอย่างที่ผู้ดูทำได้ · อัปโหลดไฟล์เข้าโฟลเดอร์ที่ได้รับสิทธิ์ |

`EDITOR` ภายในแปลว่า "แก้ไขเนื้อหาได้" แต่สำหรับลูกค้าถูกลดรูปเหลือ "เพิ่มไฟล์ใหม่ได้"
การแก้ไข ย้าย ลบ แชร์ต่อ ล็อก โอนผู้ดูแล และสร้างโฟลเดอร์ ถูกปิดตายที่ระดับชนิดข้อมูล
(`ExternalCapabilities` ประกาศฟิลด์เหล่านั้นเป็น `false` ตายตัว การเปิดในอนาคตจึงต้องแก้สัญญาของฟังก์ชันก่อน)

## การสืบทอดสิทธิ์และเส้นทางนำทาง

การเข้าถึงเกิดได้สองแบบ: ทรัพยากรถูกแชร์ให้โดยตรง หรืออยู่ใต้โฟลเดอร์ที่ถูกแชร์ให้

เมื่อมีสิทธิ์ซ้อนกันหลายชั้นในสายเดียว **สิทธิ์ที่ใกล้ตัวทรัพยากรที่สุดเป็นผู้ชนะ**
ฝ่ายภายในจึงจำกัดโฟลเดอร์ย่อยให้แคบลงกว่าโฟลเดอร์แม่ได้ โดยไม่ต้องเลิกแชร์ทั้งต้น

เส้นทางนำทางเริ่มที่โฟลเดอร์ที่ถูกแชร์ให้ซึ่งอยู่สูงที่สุดในสาย ชั้นเหนือกว่านั้นถูกตัดทิ้งทั้งหมด
ลูกค้าจึงไม่มีทางเห็นชื่อ "ไดร์ฟของฉัน" "ไดร์ฟของระบบ" หรือโฟลเดอร์ของลูกค้ารายอื่น

## วันหมดอายุและการเพิกถอน

`ResourceAccess.expiresAt` (`null` = ไม่หมดอายุ) เก็บเป็นเวลาสัมบูรณ์เสมอ
หน้าจอเป็นผู้แปลตัวเลือก "7 / 30 / 90 วัน / กำหนดเอง" เป็นวันที่จริงก่อนส่ง
เซิร์ฟเวอร์ไม่เก็บ "จำนวนวัน" เพราะจุดอ้างอิงจะกำกวมทันทีที่มีการแก้ไขสิทธิ์ภายหลัง

การตรวจสิทธิ์ทุกครั้งเทียบกับเวลาปัจจุบัน สิทธิ์ที่หมดอายุจึงถูกปฏิเสธทันทีด้วย token ใบเดิม
โดยไม่ต้องรอรอบเก็บกวาดและไม่ต้องให้ผู้ใช้ออกจากระบบ แถวยังคงอยู่ในฐานข้อมูลเพื่อการตรวจสอบย้อนหลัง

การเพิกถอนก็มีผลทันทีด้วยเหตุผลเดียวกัน - ไม่มีการจำสิทธิ์ไว้ใน token

เพดานอายุอยู่ที่ 730 วัน ถ้าตั้งใจให้ไม่หมดอายุจริง ต้องเลือก "ไม่หมดอายุ" อย่างชัดเจน

## เส้นทาง API

แยกจาก API ภายในทั้งชุด ไม่มี endpoint ใดใช้ร่วมกัน

```
GET  /api/portal/resources               หน้าแรก - ที่แชร์ให้ / อัปโหลดล่าสุด / โฟลเดอร์ที่อัปโหลดได้
GET  /api/portal/resources/:id           รายละเอียดหนึ่งรายการ + เส้นทางนำทาง
GET  /api/portal/folders/:id             เปิดโฟลเดอร์
GET  /api/portal/search?q=               ค้นหาภายในขอบเขตของตัวเอง
GET  /api/portal/resources/:id/content   เปิดดู (ไม่บังคับสิทธิ์ดาวน์โหลด)
GET  /api/portal/resources/:id/download  ดาวน์โหลด (บังคับ allowDownload)
POST /api/portal/folders/:id/upload      อัปโหลด (เฉพาะผู้ที่ได้รับสิทธิ์อัปโหลด)
```

ทุกเส้นทางผ่าน `requireExternal` ซึ่งปฏิเสธบัญชีภายในและบัญชีระบบทั้งหมด

การใช้ endpoint ภายในร่วมกันแล้วค่อยกรองผลลัพธ์ทีหลัง เป็นรูปแบบที่พลาดครั้งเดียวก็รั่ว
การค้นหาจึงเริ่มจาก "รากที่ได้รับสิทธิ์" เป็นตัวตั้ง แล้วยืนยันซ้ำรายรายการด้วยการตรวจสิทธิ์เต็มรูปแบบอีกครั้ง

## การป้องกันการเดารหัสทรัพยากร

ไม่ว่าทรัพยากรจะไม่มีอยู่จริง อยู่ในถังขยะ หรือมีอยู่แต่ไม่ได้แชร์ให้
คำตอบเหมือนกันทุกตัวอักษร: `404 PORTAL_RESOURCE_NOT_FOUND` "ไม่พบเอกสารที่ต้องการ"

ลูกค้าจึงเดาไม่ได้ว่ารหัสที่สุ่มมามีอยู่จริงหรือไม่ และไม่มีชื่อไฟล์ภายในหลุดออกไปกับข้อความผิดพลาด

## การอัปโหลดจากฝั่งลูกค้า

ใช้สายการอัปโหลดเดียวกับภายในทุกประการ - ขนาดสูงสุด ลายเซ็นไฟล์จริง checksum
การชนกันของชื่อ และความปลอดภัยของเส้นทาง **ไม่มีทางเข้าที่ตรวจน้อยกว่า**

ปลายทางมาจาก path parameter ที่ถูกตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์แล้วเท่านั้น
ไม่มี field ใดใน multipart ที่เปลี่ยนปลายทางได้ และ route ไม่รับ `parentId` จาก client เลย
(`UploadInput.portalAuthorizedParentId` ตั้งได้จาก `modules/portal` เท่านั้น และต้องตรงกับ `parentId` เป๊ะ ๆ)

| ฟิลด์ | ค่า |
|---|---|
| `createdById` | ลูกค้าที่อัปโหลด |
| `ownerId` | ผู้ดูแลของโฟลเดอร์ปลายทาง - ไม่ใช่ลูกค้า |
| `sourceType` | `EXTERNAL_UPLOAD` แสดงผลเป็น "ลูกค้าอัปโหลด" |
| `visibility` / `driveScope` | สืบทอดจากโฟลเดอร์แม่ |

ชื่อซ้ำใช้นโยบาย `KEEP_BOTH` ไฟล์ของลูกค้าจึงไม่กลายเป็นเวอร์ชันใหม่ทับไฟล์ภายใน
โฟลเดอร์ที่ถูกล็อกอัปโหลดไม่ได้ - การล็อกเป็นการตัดสินใจของฝ่ายภายในซึ่งมีน้ำหนักเหนือสิทธิ์ที่เคยมอบให้

## การเข้าสู่ระบบ

ลูกค้าเข้าสู่ระบบได้สองทาง เหมือนบุคลากรภายในทุกประการ:

- อีเมล + รหัสผ่านชั่วคราวที่ผู้ดูแลตั้งให้
- Google Sign-in เมื่อบัญชีถูกสร้างไว้แล้วและมีสถานะ `ACTIVE`

**ไม่มีการสมัครเอง และไม่มีการสร้างบัญชีอัตโนมัติจาก Google** (ข้อกำหนดเดียวกับ F9)
บัญชี Google ที่ไม่ตรงกับผู้ใช้ที่มีอยู่ยังคงถูกปฏิเสธด้วย `ACCOUNT_NOT_ALLOWED`

ปลายทางหลังเข้าสู่ระบบตัดสินจากชนิดบัญชี ไม่ใช่จากค่า `returnTo` ที่ติดมากับคำขอ
ลูกค้าไปที่ `/portal` เสมอ บุคลากรภายในไปที่ `/dashboard` เสมอ (`landingPathFor`)

## การบันทึกร่องรอย

| รหัส | เมื่อ |
|---|---|
| `EXTERNAL_RESOURCE_VIEWED` | ลูกค้าเปิดโฟลเดอร์หรือดูรายละเอียดเอกสาร |
| `EXTERNAL_RESOURCE_DOWNLOADED` | ลูกค้าดาวน์โหลดไฟล์ |
| `EXTERNAL_FILE_UPLOADED` | ลูกค้าอัปโหลดไฟล์ |
| `EXTERNAL_ACCESS_GRANTED` | เอกสารถูกเปิดให้ลูกค้า |
| `EXTERNAL_ACCESS_REVOKED` | สิทธิ์ของลูกค้าถูกเพิกถอน |

แยกจากรหัสของการแชร์ภายใน (`RESOURCE_ACCESS_GRANTED` / `RESOURCE_ACCESS_REVOKED`) โดยตั้งใจ
เพื่อให้ตอบคำถาม "เอกสารอะไรบ้างที่ถูกเปิดให้คนนอก" ได้จากบันทึกโดยตรง

`metadata` เก็บเฉพาะรหัสอ้างอิงและผลลัพธ์ ไม่เก็บชื่อไฟล์ อีเมล หรือข้อมูลส่วนบุคคล

## ข้อมูลที่ส่งออกไปฝั่งลูกค้า

`PortalResourceDto` แคบกว่า `ResourceDto` ของฝั่งภายในมาก
ไม่มี `storageKey` `checksum` `ownerId` `visibility` `driveScope` `siblingKey` `normalizedName`
ไม่มีเลขเวอร์ชันและไม่มีประวัติเวอร์ชัน (เฟสนี้ลูกค้าเห็นเฉพาะเวอร์ชันล่าสุด)

ผู้อัปโหลดถูกส่งออกเป็น "ชื่อที่แสดง" เท่านั้น ไม่ใช่อีเมลหรือรหัสผู้ใช้ -
ลูกค้าจำเป็นต้องรู้ว่าใครส่งเอกสารมาให้ แต่ไม่จำเป็นต้องรู้ทะเบียนพนักงานภายใน

## หน้าจอ

โครงหน้าของลูกค้า (`PortalShell`) **ไม่ได้ใช้ `AppShell` ของฝั่งภายในร่วมกัน**
การใช้โครงเดียวกันแล้วซ่อนเมนูตามสิทธิ์ คือรูปแบบที่พลาดครั้งเดียวแล้วรั่วถาวร
ที่นี่ไม่มีอะไรให้ซ่อน เพราะไม่เคยมีอยู่ตั้งแต่แรก - มีชุดทดสอบยืนยันว่าไม่มีลิงก์ไปหน้าภายในและ
ไม่มีการเรียก API ภายในจากไฟล์ในพื้นที่นี้

หน้าแรกมีสามส่วน: เอกสารที่แชร์กับฉัน · อัปโหลดล่าสุด · โฟลเดอร์ที่อัปโหลดได้
ไม่มีแผงสถิติ เพราะลูกค้าเห็นเพียงบางส่วนของระบบ ตัวเลขรวมจึงไม่มีความหมายและชวนให้เข้าใจผิด

เมื่อยังไม่มีอะไรถูกแชร์ให้: "ยังไม่มีเอกสารที่แชร์ให้คุณ / กรุณาติดต่อผู้ดูแลหากคุณคิดว่าควรมีสิทธิ์เข้าถึงเอกสาร"

## หน้าแชร์ฝั่งภายใน

ผู้รับสิทธิ์แยกเป็นสองกลุ่มชัดเจน: **บุคลากรภายใน** และ **ลูกค้า / ผู้ใช้งานภายนอก**
ตัวตนของผู้รับต้องไม่กำกวมแม้แต่วินาทีเดียว - การเลือกผิดกลุ่มคือการเปิดเอกสารให้คนนอก

ลูกค้ามีป้าย "ภายนอก" กำกับทุกที่ที่ปรากฏ ค่าเริ่มต้นเมื่อเลือกลูกค้าคือ "ดูอย่างเดียว" เสมอ
และมีคำเตือนบอกผลลัพธ์จริงของระดับสิทธิ์ที่กำลังจะให้

## ไดร์ฟของระบบและไดร์ฟของฉัน

กติกาเดียวกัน: ลูกค้าเห็นเฉพาะโฟลเดอร์ที่ถูกแชร์ให้โดยตรง ไม่เคยเห็นตัวไดร์ฟหรือรายการระดับรากของมัน
`canViewSystemDrive()` ปฏิเสธบัญชีภายนอกไม่ว่าจะถือบทบาทใด

โฟลเดอร์ในไดร์ฟของระบบแชร์ให้ลูกค้าได้ตามนโยบายการแชร์ที่มีอยู่ ซึ่งจำกัดไว้ที่ผู้ดูแลระบบและผู้ดูแลหลักของโฟลเดอร์นั้น
เมื่อมอบสิทธิ์ "อัปโหลดได้" ในโฟลเดอร์ดังกล่าว ลูกค้าอัปโหลดเข้าไปได้ - ถือว่าการตัดสินใจนั้นเกิดขึ้นแล้วตอนแชร์

## ถังขยะ

ทรัพยากรที่ถูกย้ายไปถังขยะหายจากพื้นที่ลูกค้าทันที ทั้งตัวมันเองและทั้งสายลำดับชั้น
ลูกค้าไม่มีทางเห็นถังขยะ ไม่มีทางกู้คืน และไม่มีทางลบอะไร

## สิ่งที่เฟสนี้ไม่ได้ทำ

- ลิงก์สาธารณะแบบไม่ต้องเข้าสู่ระบบ - ทุกคนในพื้นที่นี้ต้องยืนยันตัวตน
- ลูกค้าสร้างโฟลเดอร์เอง
- การแจ้งเตือนเมื่อมีเอกสารใหม่

# F11 - การทำให้พื้นที่ลูกค้าแข็งแรงขึ้น

## ประวัติเวอร์ชันสำหรับลูกค้า

ลูกค้าเห็นประวัติเวอร์ชันของไฟล์ที่เข้าถึงได้ **แบบอ่านอย่างเดียว** ไม่มีการกู้คืน ไม่มีการลบ
และไม่มีการอัปโหลดทับเวอร์ชันเดิม - ไม่ใช่เพราะปุ่มถูกซ่อน แต่เพราะไม่มี API ให้ทำสิ่งเหล่านั้น

```
GET /api/portal/resources/:id/versions
GET /api/portal/resources/:id/versions/:versionNumber/content
GET /api/portal/resources/:id/versions/:versionNumber/download
```

**เวอร์ชันถูกอ้างถึงด้วยเลขลำดับภายในไฟล์ ไม่ใช่รหัสของแถว `ResourceVersion`**
นี่คือการตัดสินใจด้านความปลอดภัย ไม่ใช่เรื่องความสวยงามของ URL:
เลขลำดับมีความหมายก็ต่อเมื่ออยู่คู่กับไฟล์แม่ที่ตรวจสิทธิ์ผ่านแล้วเท่านั้น
การเดารหัสเวอร์ชันของไฟล์คนอื่นจึงเป็นไปไม่ได้เชิงโครงสร้าง ไม่ใช่แค่ถูกปฏิเสธ

สิทธิ์ถูกตรวจกับ **ไฟล์แม่** เสมอ เวอร์ชันไม่มีสิทธิ์เป็นของตัวเองและไม่มีทางถูกอนุญาตโดยลำพัง

`allowDownload = false` ห้ามดาวน์โหลดทั้งเวอร์ชันปัจจุบันและเวอร์ชันเก่าเท่ากัน
ประวัติเวอร์ชันต้องไม่กลายเป็นทางลัดหลบข้อห้าม ส่วนการเปิดดูยังทำได้ตามปกติ

DTO ส่งออกเพียง: เลขเวอร์ชัน · วันเวลา · ขนาด · ชื่อที่แสดงของผู้อัปโหลด · ใช่เวอร์ชันปัจจุบันหรือไม่ · ดาวน์โหลดได้หรือไม่
ไม่มี `storageKey` `checksum` `createdById` `resourceId` หรืออีเมลของบุคลากรภายใน

## การค้นหาลึกทุกชั้น

F10 ค้นเจอเฉพาะรากที่ได้รับสิทธิ์และลูกชั้นเดียว ทั้งที่เปิดดูได้ลึกกว่านั้น F11 แก้ให้ครบทุกชั้น

การไล่ลำดับชั้นใช้ **recursive CTE** ครั้งเดียว เริ่มจากรากที่ได้รับสิทธิ์แล้วไล่ลงข้างล่าง
พร้อมสะสมเส้นทางเต็มไว้ในคอลัมน์เดียว จากนั้นอีกสองคำสั่งดึงรายละเอียดและชื่อของทุกชั้นในเส้นทาง

รวมสามคำสั่ง **ไม่ขึ้นกับจำนวนผลลัพธ์** - ไม่มีการตรวจสิทธิ์ทีละแถว

เหตุผลที่ไม่ค้นทั้งระบบแล้วกรองทีหลัง: การกรองทีหลังพลาดครั้งเดียวก็รั่ว
ที่นี่ผลลัพธ์ที่เข้าถึงไม่ได้ไม่เคยถูกดึงขึ้นมาตั้งแต่แรก ไม่ใช่ถูกดึงขึ้นมาแล้วซ่อน

รายละเอียดที่สำคัญ:

- `deletedAt IS NULL` อยู่ทั้งในจุดเริ่มและในขั้นไล่ลง โฟลเดอร์ที่ถูกลบจึง **ตัดทั้งกิ่ง**
- รากหลายอันรวมกันเองโดยธรรมชาติ และรายการซ้ำจากรากที่ซ้อนกันถูกยุบให้เหลือเส้นทางที่สั้นที่สุด
- ความลึกจำกัดที่ 32 ชั้น กันโครงสร้างผิดปกติหรือวงจร
- อักขระ `%` `_` `!` ใน คำค้นถูก escape (ใช้ `!` เป็นตัว escape เพราะ backslash ต้อง escape ซ้ำสองชั้นและอ่านผิดง่าย)
- สิทธิ์ที่มีผลคือสิทธิ์ที่ใกล้ทรัพยากรที่สุด ส่วนรากของเส้นทางที่แสดงคือสิทธิ์ที่ไกลที่สุดในสายเดียวกัน

ผลการค้นหาแสดงเส้นทางแบบตรรกะ เช่น `เอกสารบริษัท ABC / ภาษี / 2569 / กันยายน`
ชั้นเหนือรากถูกตัดตั้งแต่ชั้นค้นหา ชื่อไดร์ฟภายในจึงไม่มีทางหลุดออกมาแม้หน้าจอจะเขียนผิด

## การตรวจเส้นทางภายในแบบสร้างรายการเอง

ชุดทดสอบอ่าน **ตารางเส้นทางจริงของ Fastify** (`printRoutes`) แล้วยิงทุกเส้นทางที่ไม่ใช่ของพื้นที่ลูกค้า
ด้วย token ของลูกค้า และยืนยันว่าได้ 401 หรือ 403 ทุกเส้นทาง

เส้นทางใหม่ที่ใครเพิ่มเข้ามาในอนาคตจึงถูกตรวจโดยอัตโนมัติ ไม่ต้องมีใครจำได้ว่าต้องเพิ่มเทส
รายการยกเว้นสั้นโดยตั้งใจ (สุขภาพระบบ ข้อมูลบัญชีของตัวเอง และการเข้าสู่ระบบ) และการเพิ่มเข้าไป
ต้องเป็นการตัดสินใจที่ตั้งใจ ไม่ใช่ผลข้างเคียง

## หน้าจัดการลูกค้า

`GET /api/users/:id/portal-access` ตอบคำถาม "ลูกค้ารายนี้เข้าถึงอะไรได้บ้าง" ในคำขอเดียว:
เชื่อมบัญชี Google แล้วหรือยัง · จำนวนสิทธิ์ที่ยังมีผล · รายการเอกสารพร้อมระดับสิทธิ์ การดาวน์โหลด และวันหมดอายุ

รวมสิทธิ์ที่หมดอายุแล้วไว้ด้วยเพราะเป็นข้อมูลที่ต้องใช้ตอนตรวจสอบ แต่แยกให้เห็นชัดว่าไม่มีผลแล้ว
ไม่เปิดเผยรหัสของแถวสิทธิ์ - การเพิกถอนอ้างถึงคู่ (ทรัพยากร, ผู้ใช้) ซึ่งเพียงพอ

การมอบสิทธิ์ใหม่ยังทำที่หน้าเอกสารนั้น ๆ เพื่อให้การตัดสินใจเกิดขึ้นตรงที่เอกสารอยู่ ไม่ใช่ในหน้ารายชื่อ

## ประสบการณ์ใช้งาน

- ไอคอนชนิดไฟล์ใช้ระบบเดียวกับฝั่งภายใน โฟลเดอร์ PDF รูปภาพ Word Excel และลิงก์จึงอ่านได้แบบเดียวกันทั้งระบบ
- รูปภาพและ PDF เปิดดูได้โดยไม่ต้องดาวน์โหลด (ดึงเป็น blob พร้อม access token เสมอ - ลิงก์ตรงใช้ไม่ได้)
- ชนิดที่เปิดดูไม่ได้แสดงข้อความบอกทางออก และบอกให้ดาวน์โหลด **ก็ต่อเมื่อดาวน์โหลดได้จริง**
- การอัปโหลดแสดงปลายทางเต็มก่อนกด (`กำลังอัปโหลดไปยัง "…"`) พร้อมแถบความคืบหน้า
  ลูกค้าที่ได้รับสิทธิ์หลายโฟลเดอร์มีโอกาสส่งผิดที่ และไฟล์ที่ส่งผิดที่ลบเองไม่ได้
- ข้อความผิดพลาดของการอัปโหลดถูกแปลเป็นภาษาไทยที่บอกว่าต้องทำอะไรต่อ ไม่มีข้อความดิบจากเซิร์ฟเวอร์

# F12 - ค้นเนื้อในและประวัติการอัปโหลด

## ค้นหาจากเนื้อในเอกสาร

การค้นหาในพื้นที่ลูกค้าดูทั้งชื่อไฟล์และเนื้อในเอกสาร ผลลัพธ์ที่ตรงเพราะเนื้อหา
มีป้าย `ตรงกับเนื้อหาเอกสาร` และข้อความตัวอย่างรอบคำที่ตรงกัน

การจับคู่เนื้อหาเป็นเงื่อนไข**ภายใน**การไล่ลำดับชั้นที่เริ่มจากรากที่ได้รับสิทธิ์เท่านั้น
เอกสารของลูกค้ารายอื่นถูกตัดออกด้วยโครงสร้างของคำสั่ง ไม่ใช่ด้วยการกรองทีหลัง
และยังไม่มีการตรวจสิทธิ์ทีละแถว

มีชุดทดสอบยืนยันว่าเอกสารสองฉบับที่มีเนื้อหาเหมือนกันทุกตัวอักษรแต่คนละลูกค้า ไม่รั่วข้ามกัน

ตัวอย่างข้อความเป็นข้อความล้วน การเน้นคำทำที่หน้าจอด้วยการตัดเป็นชิ้น ๆ
ไม่มีการแทรก HTML จากเนื้อหาที่ผู้ใช้อัปโหลดที่ใดเลย

## ประวัติการอัปโหลด

หน้า `/portal/uploads` ให้ลูกค้าดูสิ่งที่ตัวเองเคยส่งเข้ามา พร้อมสถานะปัจจุบันของแต่ละรายการ

ประวัติ**ไม่ใช่ช่องทางเข้าถึงที่สอง** - รายการมาจาก "ใครอัปโหลด" แต่การเปิดดูและดาวน์โหลด

และเราไม่บอกว่ามันถูกย้ายไปที่ไหน
